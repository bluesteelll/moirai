Moirai

Moirai is a versioned graph database, written from scratch in Rust, for projects where AI coding agents do much of the work. It gives every agent on a project one place for the tasks, the project memory, the rules and the decisions, versioned with branches like git and shared by all agents at once. It is one program, moirai, with no server. It is not released yet: the project is still writing and testing its specification, and nothing can be installed.

This book explains Moirai to people who have never seen the project. It assumes that you know git, databases in general and AI coding agents such as Claude Code or Codex, but nothing of the project's own vocabulary. New terms are explained where they first appear, and the main ones are collected in the glossary.

What it does#

Moirai keeps a project's work and its memory in one typed graph. A task, a rule, a decision, a review finding and a source file are all nodes. "This subtask belongs to that task" and "this task must finish before that one starts" are edges. The engine checks every write against the schema, and it computes which tasks can start now, so nobody keeps that list by hand.

Around the graph, Moirai adds what agents working in parallel need: leases so that two agents never take the same task, branches that merge field by field, a readable copy in git, links into project files that survive moves, and a query language that every read command is built on. Each card opens the chapter that explains one part.

A first look#

Two commands from the tour, in a small fictional project. The first asks which tasks an agent may start now. The second lets an agent called dev-1 take one of them.

$ moirai ready
branch: main | rev 5 | live | 1 row
#2 task open P2 "Parse the Connection header" parent:#1
$ moirai claim 2 --agent dev-1 --start
branch: main | rev 5 -> 6 | committed c41a7d0e2
1 CALL tx.claim([#2]): lease L-2 holder dev-1, expires 2026-11-16T09:55Z; status open->in_progress
affected: none

Designed output.

The first line of each result above names the branch and the revision it was read from; a write shows the revision before and after. Every record takes one line and starts with its short id. The engine worked out the answer to ready from the task tree, the blockers and the leases. The claim gives dev-1 a lease on task #2, which every branch of the store sees, so no other agent is handed the same work.

The big picture#

Three names appear in the picture. Moirai is the product, and moirai is its one command. Klotho is the storage engine, a library inside that binary. Lachesis is the query language. In Greek myth the Moirai are the three Fates; Klotho spins the thread and Lachesis measures it.

There is no server to start and no background process. Each command opens the store, does its work and exits, and the MCP server lives only as long as the agent session that started it. Inside a git repository the store sits in git's common directory, outside every working tree, so all worktrees of the repository share one store without any setup. Git itself is never needed to run Moirai; it is only one way to keep and move a copy of the data.

Where it stands#

Milestone M0: contract and evidence

Nothing is released, and there is nothing to install yet. The project is in its first milestone, M0, "contract and evidence". The repository holds the byte-level specification of the on-disk format, a complete reference model in Rust that serves as the test oracle, test fixtures, test harnesses and the first measurement tools. The storage engine is built in the next milestone, M1, which starts after version 1 of the on-disk format is frozen with the git tag format-v1. There is no release date. How it is built, and where it stands has the roadmap from M0 to M11 and the list of what exists today.

This book therefore describes the designed system. Commands and their output are designed output taken from the specification, not recordings, and every number is a design target, not a measurement. Where the book and the specification in the repository differ, the specification is right.

How to read this book#

The chapters build on each other, but each one can be read alone. If you have ten minutes, read the first chapter and the tour.

  1. Why Moirai: the problem it solves, its requirements, its four priorities and what it deliberately is not.
  2. The graph: nodes, kinds, statuses, edges, derived state such as "ready", deletion and leases.
  3. A session, start to finish: one fictional project, command by command, with designed output.
  4. Branches, merges and history: Moirai's own version control and how parallel lanes merge.
  5. Saving into git: how the graph is written into a git repository as text and read back.
  6. File links that survive moves: pointers into project files that follow renames and edits.
  7. Lachesis, the query language: queries, versions inside queries, guarded writes and the accuracy benchmark.
  8. Working with agents: the CLI, the MCP server, skills, hooks, context packs and leases.
  9. Under the hood: Klotho: the storage engine, crash safety and the performance budgets.
  10. How it is built, and where it stands: the specification, the reference model, the tests, the roadmap and the status.
  11. Questions and answers: short answers to the questions people ask first.
  12. Glossary: every term the book uses, with a link to the chapter where it matters.
