## 0. Verdict in one paragraph

Under the owner update R1–R3 are hard requirements, so **A, B and C are deficient on this lens by construction**: none has first-class branches for all versioned data (A/C: `exp/*` rebase-on-read overlays without fork-point snapshots; B: a coordination plane that never branches), and none has a readable per-node git image (A/B/C push raw log or `hist` files as blobs under `refs/moirai/data`, which is a backup, not an image). Their engine layers are still the evidence base, and **D reuses that engine with every graft of this file's first revision written in as spec** (G1 blocking lock wait, G2/F-A1 readers stop at `committed_lsn`, G3 commit index in `hist`, G6 stamp writes only, G7 bodies in the unmapped tail, G9/X9 checkpoints outside the writer byte, G10 quiet cap, G11 zero-filled extents, G12 `current_thread` runtime, G14 orphan sweep, F-A6 30-day idempotency, F-B1 `pread` only, F-B5 no polling `watch`, F-B6 no `git merge-base` on the query path). D is therefore the best available design on this lens as well as the only one that meets R1–R3. Its new costs are all in the two layers it adds, and none of them is priced in [D §8]: **(1)** the first read of a branch in a process scans the whole interleaved log since the branch's fork — O(log bytes since fork), not O(branch ops) — so a two-week-old lane costs ~10 ms per CLI call and a two-month-old `plan/*` branch 30–60 ms, growing until a promotion that is triggered by branch op count and never fires on a quiet branch (F-D1); **(2)** `sync` copies `main`'s folded churn into every lane's history, which with ~50 lanes multiplies history growth 3–10× (F-D2); **(3)** the 4 KiB `HEAD` slot cannot hold `refs[96]` with D's ref record plus `pins[16]`, `pins[16]` cannot hold 50 branches forked at different checkpoints, and the "≤ 12 files" claim is off by an order of magnitude with pinned sets and promoted branch segments (F-D3); **(4)** the MCP server's private RSS grows by ~1 MB per lane its subagents read, so a 16-lane Workflow fan-out lands at 20–24 MB against D's own 10 MB gate (F-D4); **(5)** the image writer's Windows hygiene is incomplete: loose objects and packs need temp-then-rename, loose refs written into a live project `.git` collide with git's own lock protocol and with an antivirus filter-driver behaviour that git-for-windows itself reports (silent rollback of loose-ref writes, exit 0), reftable repositories never read loose refs at all, and `git gc` in a 1e5–1e6-object image repo is a memory and quiet-window hazard (F-D6/F-D7). All five are fixable without abandoning D's structure; two (F-D1, F-D3) change the on-disk format and must land before M1. Scores on this lens with R1–R3 enforced: **D 7.5, A 6.0, B 5.5, C 4.5** (§8).

### 1.4 Latency, MCP path (in-session, no spawn)

Overlay catch-up (one `HEAD` pread 10–170 µs + replay of new records, µs) + query (µs–ms) + durable commit 2 ms. **In A, B and C the `PreToolUse` stamp hook** is `{"type": "command", "command": "moirai", "args": ["hook","stamp"]}` with matcher `mcp__moirai__.*` ([07 §9.5 Hooks]); command hooks spawn a process (exec form avoids the shell but not the spawn): **+15–73 ms per MCP call**. C's table "MCP tool call (in-session) 0.1–5 ms" ([C §8]) and A/B's implicit claim that MCP "skips process spawns" are wrong as configured (U9). **D narrows the stamp to write tools ([D §7.2] "The stamp hook matches write tools only (G6)")**, so D's reads are spawn-free and its writes pay one spawn — the correct trade. D's per-call branch resolution "from the stamped `ctx.cwd` binding" ([D §5a.4]) is a `HEADS` probe, µs; but a subagent switching between lanes inside one session makes the server build a second overlay (F-D1 cost, once per lane per server lifetime, then incremental).

### 1.5 Writer queue under a 16-agent burst

A, B and C acquire the writer byte with `try_lock` + jittered exponential backoff ([A §4.6 step 1] 1 ms base, 2 s timeout; [B §4.5 step 1] 2 s; [C §4.4 step 1] "0.5 ms × 2^k jitter up to 250 ms total"). Ideal serialisation of 16 simultaneous 2–2.5 ms commits already puts the last finisher at **32–40 ms** (est.). Sleep-based backoff adds idle gaps (the lock sits free while every waiter sleeps) and unfairness (a waiter that has backed off to 64–128 ms loses to newcomers), so p99 of 100–300 ms is likely (est.). A's claim that "queueing delay is well under a flush time" ([A §6.2]) is wrong for its own stated burst of 16 writers. The fix is in the OS, not in a leader: Microsoft's `LockFileEx` page states "If the file handle was not opened for asynchronous I/O and the lock is not available, this call waits until the lock is granted", and for an asynchronous handle it "returns the error ERROR_IO_PENDING. The system will signal the event specified in the OVERLAPPED structure after the lock is granted" — so a bounded, poll-free wait is `LockFileEx` on an overlapped handle + `WaitForSingleObject(event, timeout)` + `CancelIoEx` on timeout (G1). **D adopts exactly this ([D §4.1 LOCK], [D §2 T2])**, which removes most of the motivation for group commit at this write volume. D's remaining contention risk is not the lock but its ref CAS wording (F-D5).

## 2. Proposal A — "Lean embedded" (score 6.0; engine 8.0 before R1–R3)

**What it gets right on this lens** (not repeated as findings): zero idle CPU by construction ("no moirai process has threads or timers", [A §2 T2], [A §6.1]) — satisfied without a flag; the smallest hot row (40 B header, cold columns split out, [A §3.1]); hand-written frozen bitsets queried in place ([A §4.4]), correctly avoiding the pure-Rust `roaring` crate that copies on deserialize [05 §10.3]; `stale` explicitly "not on the hot path" ([A §3.5]); no rename on the commit path and no truncation of a mapped file ([A §4.11–4.12]); flush failure fatal; DST with crash-point enumeration and 16-writer kill loops as the M0 exit gate ([A §9]); honest per-row budget derivations ([A §8]).

**Under R1–R3.** A's branches are "delta overlay[s] that rebase on read: the branch view is the current trunk state with the branch's ops applied on top" ([A §5.2]) — the opposite of git-like isolation; the isolated form is `--pinned`, which "freeze[s] the trunk view at the fork sequence by reverse-applying trunk commits since the fork (cost O(trunk ops since fork), on demand)" — per read, per process, with no fork-point snapshot, so a 14-day branch reverse-applies ~14k commits on every CLI call and its overlay holds every key trunk touched since the fork (est. 10–40 ms and MBs). That does not scale to 50 live branches; D's pins are the missing structure. Coordination ops are refused on branches ([A §5.4]), which R1 forbids. R3 is absent: M5 "publish log and base files as git blobs under `refs/moirai/data`" ([A §5.7]) is a backup, not a diff-friendly per-node image, and A's 64-bit random `uid` ([A T4]) is too small to be the store-independent identity an image needs (cheap to widen). The findings below stand for A as written; D fixes each of them.

### F-A1 (crash safety, serious) — Lock-free readers apply commits that may not be durable

[A §4.8 Open path, step 3]: "scan from `committed_lsn` to the end … any complete commit beyond `HEAD.committed_lsn` is applied and `HEAD` is treated as stale". `committed_lsn` is advanced only after the flush ([A §4.6 steps 6–7]), so the region beyond it may hold a record that a writer appended and has not yet flushed. A reader takes no lock, so it cannot know whether that writer is alive and about to flush, dead before flushing, or finished. **Failure scenario:** dev#1's CLI appends `Claim{#12}` (WriteFile returns; bytes sit in the OS cache), then the harness kills the process tree before `NtFlushBuffersFileEx` (the owner "kills processes wholesale" [08 §2]; Claude Code "re-signals" agents on stop [08 §8.1]). The orchestrator's MCP server opens 5 ms later, applies the record, and answers `ready` with "#12 claimed by dev#1"; an OS crash follows within the write-back window (the development machine has experienced such crashes [02 §9]) and the dirty page is lost. After reboot #12 is unclaimed and the orchestrator's Workflow journal disagrees with the store. This is exactly the anomaly redb forbids: two-phase commit is mandatory in its multi-process modes "to ensure that committed pages are flushed before the transaction becomes visible to another process" [08 §3.3]. It silently weakens A's I11 ("every acknowledged commit is durable") into "every *observed* commit is durable". **Fix (cheap):** readers stop at `committed_lsn`; only a process holding the writer byte scans forward, re-flushes what it finds (one 2 ms flush, recovery path only), publishes `HEAD`, and only then consults the idempotency table (G2; [21 X2]; adopted by [D §4.3]).

### F-A2 (performance, serious) — Writer-queue convoy under bursts (see §1.5)

[A §6.2]: "Expected hold time 2–3 ms per commit; with 16 agents … queueing delay is well under a flush time". Not with sleep backoff: a Workflow fan-out of 16 developers each calling `moirai claim` at t=0 has an ideal last ack at ~40 ms; with 1 ms-base doubling backoff and 16 contenders, several waiters reach 32–128 ms sleeps while the lock is free, and the p99 lands at 100–300 ms (est.). The blocking `LockFileEx` wait (G1) fixes it without a leader.

### F-A3 (performance + crash safety, serious) — Rollups run inside the writer lock in whichever process trips the threshold

[A §4.10]: "Who does it: the process that crosses the threshold, inside its writer lock, or the long-lived MCP server at the end of a request". Cost "0.1–0.3 s at 1e5, 1–3 s at 1e6" [05 §7]; the owner's 3-year scale is 0.3–0.5 M nodes [02 §12.6] → 0.3–1.5 s (est.). **Failure scenarios:** (a) at ≥ ~0.7 M nodes a rollup exceeds A's 2 s writer timeout and every concurrent writer exits 7 for the duration; (b) the process that trips it may be a `SubagentStop` or `UserPromptSubmit` hook with a 5–10 s harness timeout ([A §7.4]); if the harness kills it mid-rollup, the writer byte is held until the OS releases it "depending upon available system resources" (LockFileEx docs, [08 §4 W2]) and a partial `seg.base.G+1` temp file is left behind; (c) the rollup rebuilds the `commits` index that lives in the base segment (28 B per commit, [A §4.4]) and the tier-2 FTS, so rollup cost is O(history) + O(text), not O(N): at 1e7 commits +280 MB of sequential write (est.), and tokenising 1e5 × 1 KiB bodies is ~1–2 s (est.). A's "No step is O(node count) or O(history)" ([A §4.8]) is true for open only. **Fix:** delta checkpoints automatic and bounded; rollups only on explicit `compact` or in the long-lived MCP server after a request; commit index per sealed log file (G3); tier-2 postings per delta segment (G9).

### F-A4 (Windows, minor) — Preallocation via `SetEndOfFile` does not make commits "overwrite in place"

[A §4.12]: "Log growth by `SetEndOfFile` in 16 MiB steps". On NTFS a write beyond the valid-data length still advances VDL in the MFT record, i.e. a metadata update per commit, so the 0.1 ms saving measured for overwrite-vs-append [05 §2.2] is not obtained. Durability is fine: `FLUSH_FLAGS_FILE_DATA_SYNC_ONLY` is documented as "Only metadata that is necessary for data retrieval will be flushed (timestamp updating will be skipped as much as possible)" (Microsoft Learn, `NtFlushBuffersFileEx`), which covers EOF/VDL. To get overwrite-in-place, zero-fill each new extent once plus one full `FlushFileBuffers` — the PostgreSQL WAL pattern [05 §6.2] (G11; D's 64 MiB extents cost 30–60 ms once per ~150k commits, est.).

### F-A5 (Windows, unverified) — Defender cost of the CLI's open-append-flush-close pattern

Both flush measurements ([05 §2.2], [08 §2]) wrote to a scratch file through one handle kept open. A CLI commit opens the active `log.NNN` (16–64 MiB), appends, flushes and **closes** it; Defender real-time protection scans modified files on close and "charges per file opened" [05 §6.4]. SQLite's finding that AV "impacts SQLite writes very little" [05 §6.4] suggests the cache-manager path is cheap, but that was not measured here for a large, constantly modified file. Add "open→append→flush→close on a 64 MiB file, Defender on, n = 200" to M0 (G8; D lists it). If it is tens of ms, the CLI path needs the MCP server more than any proposal admits.

### F-A6 (crash safety, minor) — Idempotency retention of 7 days

A Workflow resumed after > 7 days re-runs every completed agent [07 §4.1] and replays writes that are no longer deduplicated. C's 30 days ([C §6.5]) costs 32 B × 30 days × ~1k writes/day ≈ 1 MB. Take C's value (D does).

### F-A7 (consistency, trivial) — `LOCK` "0 B data" vs holder info at offset 4096 ([A §4.1] vs [A §4.6 step 1])

Harmless as long as no lock range ever covers those bytes (mandatory locks would then fail other processes' `ReadFile`, [05 §6.3]). D places diagnostics at offset 2048 "never inside a locked range" ([D §4.1]).

## 3. Proposal B — "git-faithful" (score 5.5; engine 7.0 before R1–R3)

**What it gets right on this lens:** readers replay only "(last_seen_lsn, committed_lsn]" ([B §4.6 step 3]) — the 2PC-safe rule A lacks; "no file is ever truncated or renamed over while it can be mapped" ([B §4.1]); M0 = oracles and format spec *before* the engine ([B §9]); content-addressed, dictionary-compressed blobs with dedup ([B §4.1]); history retired into zstd-framed `hist.NNNN` with a per-frame commit index ([B §4.8]) — bounded, never rewritten; the fullest Windows list (DACL, `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, errors 5/32 retry, no auto-create on a store miss, [B §4.9]); lock-release-delay injection in its simulation ([B §9 M1]). D's engine is B's with the fixes below.

**Under R1–R3.** B's coordination plane "never branched; visible to all worktrees at once" ([B §3.1]) is the direct opposite of R1; its `exp/` branches "fork everything including the coordination plane as a snapshot" ([B §5.3]) with no cost stated — a literal snapshot at 1e5 is 12–55 MB per branch (index-only to whole store, [B §8]), which at 50 branches is 0.6–2.7 GB of disk, and if it is instead an overlay it is A's rebase-on-read with the same `--pinned` problem. B's sparse lane overlays, O(lane ops) per process, are the cheapest per-lane cost of the four for knowledge-only lanes (F-B8), but they cover half the data. R3 is absent: `moirai push` "writes retired `hist.NNNN` frames and a `head.json` as git blobs" ([B §5.6]) — opaque binary blobs, not a readable image, and `pull` "imports foreign commits" only from the same format. The findings below stand for B; D adopts F-B1, F-B3, F-B5, F-B6 and F-B7's fixes.

### F-B1 (Windows, serious if taken) — "read the mapped HEAD page" is the one hazard the reports warn against

[B §4.6 step 1]: "pread the two HEAD slots (or read the mapped HEAD page; ~0.17 ms cold, nanoseconds warm)". `HEAD` is written by writers with `WriteFile`; reading it through a mapped view is exactly the "mapped views and ReadFile/WriteFile are not necessarily coherent" case [05 §6.2]. **Failure scenario:** a follower MCP server polls the mapped slot, sees a stale `slot_seq` for a window, and answers `ready` from a state one commit old right after another process's `complete` — bounded staleness, but it violates B's own "monotonic reads keyed by committed_lsn" story. The `pread` is 10–170 µs; keep it, delete the mmap option (D: "`HEAD` read only by `pread`" [D §4.3]).

### F-B2 (performance, potentially serious; unspecified) — Where the active log's commit-id side index lives

[B §4.7]: "commit id → lsn: fanout(256) + sorted [(id16, lsn)] in `hist` and in the active-log side index". If the "side index" is per process and built by scanning the active log on open, open becomes O(active log ≤ 64 MiB), i.e. tens of ms, contradicting "no O(history) work on open" ([B §8 gates]). If it is a file, it is a mutable file that must not be mapped and must be written under the writer lock. State that it is lazy or part of the log-segment seal (D inherits this gap: [D §4.4] lists `GITMAP` and `REFS` sections but not the active-log commit index).

### F-B3 (Windows, unspecified) — Where a body lives between commit and checkpoint

[B §4.3] `SetBody` carries only blob hashes; [B §4.1] says `blobs.NNNN` is "mmap read-only". A body written now must exist somewhere readable before the next checkpoint: either inline in the op log (then the 4 MiB tail threshold trips every ~100 large writes and every reader's tail replay copies bodies it never reads), or appended to `blobs.NNNN` while other processes hold read-only views of it — `SetEndOfFile` on a mapped file fails with `ERROR_USER_MAPPED_FILE` [08 §4 W4]. C's rule — bodies inline in the (unmapped) log tail, copied into the sealed snapshot at checkpoint ([C §4.2]) — is the safe one; body bytes need their own threshold (G7; adopted by [D §4.1]).

### F-B4 (performance, serious) — Automatic rollup by ratio inside a CLI/hook writer

[B §4.8]: rollup "at 1e6 only on explicit `moirai gc` or when deltas exceed 25% of base" — the second clause is automatic and runs wherever the threshold trips, with the same 0.1–0.3 s / 1–3 s costs and the same 2 s timeout as F-A3. Same failure scenarios, same fix (D: rollup "only on explicit `moirai gc` or in the long-lived MCP server after a request" [D §4.3]).

### F-B5 (idle CPU, minor but a rule violation) — `moirai watch` polls

[B §6.1]: without a leader, `watch` "sleeps 250 ms between HEAD reads: ~0 CPU". Four preads per second is ~0.07 % CPU (est.), but it *is* polling, which [02 §9] and [02 §13] forbid, and it keeps a process awake during quiet windows. Make `watch` leader-only (D M6) or drop it from the quiet-window profile.

### F-B6 (latency, serious in `pack`/`brief`) — `git merge-base --is-ancestor` on the query path

[B §3.6 `stale`]: "computed lazily per query with a cached (sha, sha) → bool ancestry table filled by `git merge-base --is-ancestor`" at **74 ms per call** (measured, [08 §2]). **Failure scenario:** the tester's `pack #89 --role tester` after a rebase of `u/l5np` with 30 measurements pinned at 30 distinct shas = 2.2 s inside a hook with a 5–10 s timeout. A's rule ("checked at `reconcile`/`stale`, not on the hot path", [A §3.5]) is right; C's shared lazy-fact cache in the log ([C §4.7]) is the right place; D uses its own pack reader plus C's cache ([D §5c]) and never spawns git (F-D13 notes the remaining cost).

### F-B7 (crash safety, wording) — "re-published by the next opener"

[B §4.5]: a record "flushed but never published is re-published by the next opener (the client saw no ack and retries with its idempotency key, which hits the `IDEM` index)". Readers do not write `HEAD` and do not look beyond `committed_lsn`, so the "opener" must be the next **writer**, and it must scan forward and re-publish *before* it evaluates the retry's idempotency key — otherwise the retry misses `IDEM`, appends a duplicate, and the orphan record is later published too. D states the order ([D §4.3] "adopt and re-flush complete unpublished commits, republish `HEAD`, *then* evaluate the idempotency key").

### F-B8 (RAM/latency, minor) — Per-process lane state

Live-rebased lane reads need the lane overlay, "rebuilt on open by walking the lane ref's commit chain down to `base_lsn` (O(lane ops))" ([B §5.3]). One session's MCP server serves subagents across worktrees [08 §2], so it holds one overlay per active lane (≤ 1 MB each at 10k ops, est.), and every CLI call from a lane pays the rebuild — a chain walk of random `pread`s (10–170 µs each): 0.2–1 ms warm at 2k ops, up to 0.1–0.5 s cold at 10k. Bounded and priced; it is the cost D inherits in a different shape (F-D1: sequential scan of everything instead of random reads of the chain).

### F-B9 (performance, minor) — `show #N@commit` in `hist`

[B §8]: "10–30 µs". Chains that reach into `hist.NNNN` decompress a 256-commit zstd frame (~77 KB at 0.3 KB/commit → ~50 µs at 1.5 GB/s, est.) per hop; a 10-hop chain is 0.1–0.5 ms. Fine; the number is optimistic (D's table already says "≤ 0.1–0.5 ms per cold frame").

## 4. Proposal C — "Agent-workflow first" (score 4.5; engine 6.0 before R1–R3)

**What it gets right on this lens:** leases, idempotency keys and cursors are log records, so "they survive any process death" ([C §4.9]); an explicit per-operation durability class table ([C §2 T8]); group commit with "no timer runs when no write is pending" ([C §4.4]); quiet mode also implied by a lane's `measuring` status ([C §4.8]); `stale` cached and shared through the log ([C §4.7]); an explicit "idle CPU 0 % over 60 s" gate ([C §8], [C §9 M3]).

**Under R1–R3.** `exp/*` branches are "a ref plus a delta overlay (the same overlay structure as the tail) forked at a commit; reads on `exp/x` consult the overlay first" ([C §5.2]) with no fork-point pin and "rebuilt by replay, never promoted to their own snapshot in v1" — A's mechanism without even A's `--pinned` option, deferred to M5. R3 is "Optional M7: publish history as git objects under `refs/moirai/data`" ([C §5.6]) — a backup. The v1 engine also fails at the owner's scale as written (F-C1/F-C2).

### F-C1 (performance + availability, fatal at ≥ 1e5 as written) — Full base rewrite inside the writer lock with a 250 ms writer timeout

[C §4.1]: "v1 rewrites the base at every checkpoint because it is ≤ 30 MB at 1e5"; [C §4.4 step 9]: "run a checkpoint synchronously before unlocking (≤ 30 ms at 1e4, **0.1–0.3 s at 1e5**)"; [C §4.4 step 1]: writer wait "0.5 ms × 2^k jitter up to **250 ms total**; on timeout exit 7". **Failure scenario:** at 1e5 nodes, dev#3's `complete` trips the 4,096-op threshold and holds the writer byte for 100–300 ms while rewriting 30 MB (plus Defender scanning the new file on close, unmeasured); every other writer that arrives in that window — a 16-agent `apply` fan-out, the orchestrator's `claim` — exhausts its 250 ms budget and exits 7. At the owner's 3-year scale (0.3–0.5 M nodes) the rewrite is 90–150 MB and 0.3–1 s (est.), and the failure is deterministic. The threshold also counts inline bodies toward the 4 MiB tail ([C §4.2]), so a burst of 16 KiB result bodies trips a full rewrite every ~250 writes. **Fix:** delta segments from M1, rollups explicit/MCP-only, body bytes on a separate threshold (G7), writer wait ≥ 2 s with a blocking wait (G1) — all of which D does.

### F-C2 (Windows crash behaviour, serious) — 250 ms lock timeout vs delayed lock release

When a writer is killed the OS releases its byte-range lock after a delay that "depends upon available system resources" (LockFileEx docs; [08 §4 W2]) — on a machine at 30–100 % CPU with 16 agent processes this can plausibly exceed 250 ms. **Failure scenario:** `taskkill` of one lane's process tree mid-commit → for the release window every writer in every other lane exits 7. A/B/D's 2 s bound absorbs this; C's does not, and nothing in C retries automatically on exit 7.

### F-C3 (RAM/layout, minor but wrong arithmetic) — CSR carries `prop_idx` in both directions; hot-set headline understated

[C §4.3]: 9 B per edge per direction, 63 B/node at 3.5 edges, for an edge property that exists on `cites` only. The headline "Hot set ≈ 100 B/node" contradicts C's own table (≈ 138 B). Store edge props as a sparse sorted side table (A/B/D) and the hot row drops to ≈ 95 B.

### F-C4 (RAM, wrong dependency claim) — "roaring, frozen (queryable in place)"

[C §4.3] with `roaring` in the allowed-crate list ([C §2 T10]). [05 §10.3]: "Pure-Rust `roaring` 0.11.5 deserializes (copies)"; only CRoaring's frozen layout (`croaring`) is queryable in place. As written, every bitmap read from a mapped snapshot allocates a private copy (≤ 128 KiB per set at 1e6; C has ~170 sets → potentially several MB of private RSS per process on a `find`). Hand-write the frozen container (A/B/D) or accept `croaring`.

### F-C5 (crash safety, serious in leader mode) — Forwarded writes without a mandatory idempotency key

[C §6.1]: followers forward writes to the leader over the pipe; [C §6.5]: keys are optional except for `apply`. **Failure scenario:** the leader is killed by session stop after appending and flushing a forwarded `remember{finding}` but before acking; the follower "retries, then writes directly" → the finding is created twice. Fix: the pipe client generates a random 128-bit key for every forwarded write that lacks one (G13; D M6 "forwarding with auto-generated keys").

### F-C6 (performance, minor) — Group commit adds up to 5 ms to a solo write

[C §4.4]: "the leader accumulates arrivals for ≤ 5 ms or until 64 records". A lone writer waits up to 5 ms before its 2 ms flush. Pipelined group commit gives the same amortisation with no added latency and no timer (G13; D M6 "pipelined group commit").

### F-C7 (correctness of GC bookkeeping, minor) — Reader registry aliases by `seq % 1024`

[C §4.1 LOCK]: readers take a shared lock on byte `2 + (seq % 1024)`. A reader at seq 5 and one at seq 1029 share a byte; the "oldest live snapshot" is a lower bound modulo 1024, so the grace period must still exist, and [C §6.1] says readers take no locks anyway. Drop the registry in favour of A's delete-pending rule (D does).

### F-C8 (crash safety, wording) — "lazy … flushed by the next durable commit or process exit"

[C §2 T8]. A killed process does not flush at exit. Say "by the next durable commit"; treat lazy records as lost after power loss (C's §4.9 already does).

### F-C9 (RAM, trivial) — 28 node kinds × per-kind, per-status bitmaps

~170 sets vs A/D's ~80. Worst case 128 KiB per set at 1e6 (21 MB vs 10 MB, mapped). Immaterial; fewer kinds are cheaper to keep consistent.

## 10. Proposal D — "Branches + git image" (score 7.5)

**What it gets right on this lens** (not repeated as findings): every revision-1 graft is in the spec, not optional (§0); checkpoints and promotions run under the maintenance byte with the writer byte taken for microseconds ([D §4.3]), which is the single biggest liveness fix over A/B/C; readers stop at `committed_lsn` and the writer scans-adopts-republishes before evaluating idempotency ([D §4.3]); blocking `LockFileEx` wait with diagnostics outside the locked bytes ([D §4.1]); bodies in the unmapped tail with their own 32 MiB threshold; commit index in `hist`; rollup only on `gc`; `watch` leader-only; no `git` process anywhere in the core and provenance from two small text reads ([D §5c]); the image is written by moirai's own loose/pack/bundle writer with packs above a threshold and the loose/pack threshold explicitly deferred to an M0 measurement ([D §4.5], [D §5b.8]); exports/imports "refuse while quiet unless `--force`" ([D §6]); fork is one durable commit with zero copying and pins keep old checkpoint sets alive across rollups ([D §5a.3]); per-process overlays keep the multi-process protocol unchanged ("nothing is shared except mapped sealed files", [D §6]); `HEAD` per client is a `HEADS` table probe, not a file per worktree; the M1 gate already includes "50 branches × 2k ops each readable within budget" and the M0 list includes loose-object create cost, Defender close cost, blocking-lock contention and the dictionary ratio ([D §9]). The remaining findings are in the branch and image layers.

### F-D1 (performance, serious; format) — The first read of a branch scans the whole interleaved log since the fork

[D §5a.3 Overlay build]: "replay `ops(main, (P, fork_seq])` and `ops(X, …)` from `log`/`hist` (sequential reads …). Bounded by the checkpoint spacing (≤ 4,096 ops) plus the branch's own ops (owner's lanes: ~1–3k ops per lane est.); **1–5 ms est.**". The trunk part is bounded. The branch part is not: there is one store-wide log ("the commit is appended with `ref` = the client's current branch", [D §4.3]; "`seq` is store-wide over all branches", [D §5d.1]), so the only way to find `ops(X, (fork_seq, tip])` sequentially is to scan every record from `fork_seq` to the head and keep the ones whose `ref` is X. The cost is O(log bytes since fork), i.e. O(everyone's traffic since the fork), and it is paid on the first read in *every process* — for the CLI that is every call. At ~1k commits/day store-wide (D's own estimate) and 0.3–0.6 KB per commit: 0.3–0.6 MB per day of branch age to read and header-parse; `hist` frames must be decoded whole (zstd frames of 256 commits) but decode at ~1.5 GB/s, so the scan is ~1–2 ms per MB either way (est.). **Numbers:** a 1-day lane ≈ 2 ms (fine); 7 days ≈ 4–8 ms; **14 days ≈ 8–15 ms; a 60-day `plan/*` branch ≈ 30–60 ms**, versus D's 1–5 ms and its "≤ 10 ms on a lane after overlay build" gate, which excludes the build itself. **Failure scenario:** the owner's lanes live for days to weeks ([08 §2]: 44 worktrees, 107 branches); a tester in a 3-week-old lane runs `moirai pack #89 --role tester` from Git Bash: 109 ms wrapper + 40 ms spawn + **20 ms overlay scan** + 5 ms pack — the engine share triples and, unlike the spawn, it grows with lane age and with every other lane's traffic. Promotion, which would reset the scan start to `promoted_seq`, triggers "when `ops_since_fork` > 8,192 or the overlay exceeds 8 MiB" ([D §5a.3]) — a branch with 500 ops never promotes, however old. **Fix:** G15 (per-ref op index: `prev_on_ref` in the commit header plus per-ref lsn lists in every `Checkpoint` record, so the builder `pread`s only its own commits) and G16 (promotion by age). Both are M1 format items; G15 costs ~8 B per commit and a few KB per checkpoint record.

### F-D2 (disk + RAM, serious) — `sync` copies `main`'s folded churn into every lane's history

[D §5a.3]: "Merging `main` into X (`moirai sync`) does *not* move `base_pin`; it appends a merge commit on X whose changeset is `main`'s ops since the LCA, so the overlay grows by those ops." [D §5a.7 step 6]: the merge commit carries "the merged ops". So every `sync` writes a copy of `main`'s changeset since the last sync into the log, once per lane. **Arithmetic (est.):** `main` churn ≈ 1k commits/day × 2–6 ops, folded per key to ~1.5–4k keys × 20–40 B ≈ **30–160 KB per sync per lane**; 50 lanes syncing daily ≈ 1.5–8 MB/day ≈ 0.5–3 GB/year raw, 0.2–1 GB/year after `hist` — against 0.1–0.2 GB/year for the trunk-only history in [B §5.1]/[D §8]. That is a 3–10× inflation on a disk the owner describes as starved by build caches [02 §9], and it lands in the same `log`/`hist` files every branch scan must read (F-D1 compounds it). Each `sync` also inflates the lane's overlay by the same ops, so a daily-synced lane crosses the 8,192-op promotion threshold every 2–5 days (10–100 ms each, outside the writer byte — fine). **Fix:** G17, merge-by-reference: the `sync` commit stores `main_base := M` and only the resolution ops for keys both sides touched (typically dozens, not thousands); the branch view replays `main`'s ops from `main`'s own log up to `M`, which G15 makes O(main commits) with sequential reads. The three-way base rules for a second `sync` are [21]'s lens.

### F-D3 (format, serious as spec; minor in impact) — `HEAD` slot, pin table and file-count arithmetic

[D §4.1]: the `HEAD` slot "gains `epoch u64`, `pins[16]`, `n_heads`, `default_ref`, `image_cursor[4]`" while [D §5a.2] keeps "`HEAD.refs[96]` inline". B's slot is already 4,048 of 4,096 B (56 B of scalars + 8 × 29 B segments + 96 × 39 B refs + 16 B), and D's ref record needs `kind, commit_id, lsn, base_pin, fork_commit, fork_seq, ops_since_fork, promoted_seg, gen` ([D §5a.1]) ≈ 57 B, not 39 B: 96 refs alone are ~5.5 KB. The slot does not fit. `pins[16]` cannot hold 50 live branches forked over more than 16 distinct checkpoints (1–2 checkpoints per day at 2–6k ops/day; the owner's lanes are opened over weeks), and D does not say what the 17th fork does. Pins are described per *segment set* but their retention effect is per *file*: each pinned set keeps its `d1..dK` delta files alive across `main`'s tiered folds, so 50 pins spanning ~40 checkpoints retain 30–120 delta files plus 2–4 bases — the "≤ 12 per store" of [D §4.1] is 50–130 with promoted branch segments (`seg.b<refsym>.K`) on top. Disk is small (~10–30 MB of retained deltas at 1e5, est.); Defender charges at creation, not for sealed files nobody opens; the cost is a wrong spec and a hard cap. **Fix:** G18 — `HEAD` holds `refs_lsn`/`pins_lsn`/`heads_lsn` and the small scalars; tables live in `RefTable`/`Pin`/`ClientHead` records folded into segment sections; pins refcount segment *files*, unbounded; `doctor` reports pinned files and their holders. One extra `pread` per open (10–170 µs).

### F-D4 (RAM, moderate) — MCP server private RSS scales with the lanes its subagents read

[D §8]: "Private RSS, MCP server … + one overlay per branch its subagents read (≤ 1 MB each; typically 1–3)". [D §5a.4]: "The MCP server resolves per call from the stamped `ctx.cwd`, so subagents in different worktrees read different branches through one server." The owner's Workflow fan-out is p90 14 agents per run, one worktree per lane, 16 concurrent by default, all sharing the parent session's MCP connection [02 §5.1], [08 §2]. **Arithmetic:** 16 lanes × ~0.9 MB (6k ops × 150 B) ≈ 15 MB on top of 4–8 MB ≈ **20–24 MB private at 1e5**, against D's CI gate "private RSS ≤ 10 MB MCP at 1e5" ([D §8]). Absolute RAM is still fine against 1.8 GB free; the gate is what is wrong, and `ready --across` over an unlisted set of refs builds one overlay per ref in the calling process — 50 refs ≈ 0.2–1 s of F-D1 scans and 50 MB (est.). **Fix:** G19 (K-overlay LRU, restated gate, `--across` limited to promoted branches' `TOUCH` bitmaps unless refs are listed).

### F-D5 (liveness, serious if read literally; wording) — Ref CAS on `old` under concurrent same-branch writers

[D §5a.2]: "Ref update is compare-and-swap on `old`; a stale `old` (another process committed on the same branch first) fails with exit 4 and the current tip. Two agents on one lane branch therefore serialize on the writer byte exactly as on a shared trunk." The two sentences pull in opposite directions. If `old` is the tip the client observed *before* taking the writer byte, then a 16-agent fan-out on `lane/x` (D's own walk-through step 6 claims two tasks on one lane and dispatches 16 Workflow agents into lanes) has 15 losers on the first round, each retrying with exit 4 — the convoy of §1.5 returns as application-level retries with a full spawn per retry (15–73 ms). On the shared trunk A/B/C never fail a plain write for this reason: the writer re-reads the tail under the lock and applies on top. **Fix:** G20 — the commit's parent is the branch tip *after* tail replay under the writer byte; a CAS failure can only come from an explicit `--if-tip`. If D meant that already, [D §5a.2] must say it.

### F-D6 (Windows + crash safety, serious) — Image writer file hygiene: objects, packs, live-repo refs, reftable

Four gaps in [D §5b.6]:

1. **Loose objects.** Step 4 writes loose objects; step 6 says "objects are written and flushed before refs move; a crash leaves unreferenced objects at worst (git-safe)". That is true only if an object never exists at its final content-addressed name before it is complete: git skips writing an object whose file already exists, so a torn `objects/xx/<hash>` left by a kill mid-write is a permanent corrupt object until `git fsck` finds it. Git itself writes `tmp_obj_XXXXXX` and renames. D specifies temp-then-rename for ref files only. The same applies to packs (`tmp_pack_*` → `pack-<hash>.pack`, `.idx` written and renamed *after* the pack; git ignores a `.pack` without an `.idx`). On this machine the rename is the W3 hazard (Defender/indexer sharing violations, errors 5/32) and needs the bounded retry D already uses for refs.
2. **Loose refs in a live project `.git`.** Step 5: "write the new value (`refs/moirai/heads/<name>` loose ref file via write-temp-then-`MoveFileEx` …); `packed-refs` is left alone, git resolves loose over packed". The owner's 44 worktrees and merge-queue scripts run git continuously; git's own ref writes and `pack-refs` (run by `gc --auto`) use `<ref>.lock` files for mutual exclusion and verify a loose ref's value under that lock before pruning it. A moirai writer that does not take `<ref>.lock` can interleave with `pack-refs`; the separate-repo default avoids this, but D lists the project repo as a supported destination. Worse, and independent of git's protocol: git-for-windows issue #6396 (Git 2.55.0.windows.3, machines with antivirus real-time protection — Windows Defender and a Sangfor aTrust client are named) reports that a loose-ref write "is reported complete (exit 0, no stderr), then silently rolled back after the file handle closes", and that "any pre-existing loose refs under `.git/refs/remotes/origin/` are DELETED by the operation, so ref resolution falls back to a stale packed-refs snapshot". Whatever the root cause on that machine, D's CAS ("verify it equals the last exported oid … write the new value") has no read-after-write step, so a rolled-back ref would be discovered only by the *next* export's CAS failing with exit 6 and the remedy "`moirai image import`" — which would then import the store's own commits back as if they were foreign. **Fix:** G21 — git's `.lock` protocol for refs in any repo git also writes, read-after-write verification with one retry, `image doctor` comparing `gitmap` against the refs.
3. **Reftable.** The gitformat-reftable specification says refs "are stored in the `$GIT_DIR/reftable/` directory", "Readers must read `$GIT_DIR/reftable/tables.list` to determine which files are relevant", and a reftable repository keeps `.git/refs/heads` as "a regular file" placeholder for old clients. A loose file written under `refs/moirai/heads/` in such a repository is never read by git; D's writer succeeds and exports nothing visible. Git 3.0 makes reftable the default for new repositories (~April 2027, [04 §3.1]). **Fix:** G22 — detect `extensions.refStorage = reftable`, delegate to `git update-ref --stdin` when git is present, refuse otherwise; `--create` writes `refStorage = files` explicitly.
4. **Read-after-write for objects too.** A cheap variant of the same defence: after the rename, `CreateFile`+read the first bytes of the object (0.17 ms) and compare the header; it catches the #6396 class for objects as well.

None of this changes D's structure; all of it belongs in [D §5b.6] before M4.

### F-D7 (Windows + quiet mode, moderate) — Loose objects per commit, and `git gc` in the image repo

[D §5b.6 step 4]: loose "when the export produces ≤ 64 objects (typical incremental run …)"; [D §5b.10]: 11 loose files per incremental commit at "~5–35 ms incl. Defender per-file cost". My recount (§1.7): ~32 KB raw across 11 files (SHA-1) and **15–60 ms** with a per-object flush and Defender scan-on-close (est., unmeasured — D's own M0 item). A per-commit export cadence would create ~4M loose files per year in the image repo, two orders of magnitude past `gc.auto = 6700` [04 §3.1]; a per-run cadence (D's default) batches into packs above 64 objects, i.e. above ~6 commits, and yields tens of packs per week; git's `gc.autoPackLimit = 50` then triggers a full repack on the next git command that runs `gc --auto` (fetch, merge, commit — not push). `git repack` memory is "the limit multiplied by the number of threads used by git-pack-objects" (git-repack docs) with `pack.windowMemory` unlimited by default and `pack.threads` = 16 on this CPU; at 1e5–1e6 objects that is minutes of CPU and hundreds of MB to GBs of RAM on a machine with 1.8 GB free, and it would run whenever the owner (or a hook) fetches into the image repo — including during a quiet window, which moirai's own quiet flag cannot see. **Fix:** G23 — packs by default above ~8 objects (from the M0 measurement), batched runs, and an image-repo config written by moirai (`gc.auto = 0`, `gc.autoPackLimit = 0`, `pack.threads = 2`, `pack.windowMemory = 64m`) with gc only through `moirai image gc`, refused in quiet mode. The loose path stays for tiny runs and for `--loose`.

### F-D8 (RAM, moderate; unstated) — Export and import RSS

[D §5b.6 step 3]: "build the tree by applying the changeset to the **exported tree of its first parent** (kept as an in-memory map `path → blob id` for the working set …)". For a full export at 1e6 that map is ~80–100 MB private (36-byte names + 20/32-byte oids + map overhead) plus 30–40 MB of pack-index entries; at 1e5 ≈ 12–15 MB (§1.7). For an *incremental* export the same sentence, read literally, materialises the whole map to touch three paths. [D §8] lists no export or import RSS, and the CI gate is 4 MB CLI / 10 MB MCP. Import of a full image similarly holds the complete tree diff (all paths) at ~80 MB for 1e6. **Fix:** G24 — lazy parent-tree reads (root + touched mid + leaf from the object store, ~20 KB), streaming pack writing with the index entries as the only O(objects) structure, and explicit-command RAM budgets in [D §8].

### F-D9 (crash safety, minor; wording) — The store epoch as specified protects nothing

[D §4.5]: "the epoch in headers rejects records from a restored older copy of the store"; [D §4.1]: "`epoch u64` (random at `init`, repeated in every record header)". A restored older copy of the same store carries the same epoch; nothing is rejected. The epoch is useful only if it changes on restore/repair (then stale records in an extent beyond `committed_lsn` from the pre-restore life are rejected) — and G11's zero-fill already makes fresh extents safe. **Fix:** G25 — re-roll on `init`, `doctor --repair`, `restore`; zero-fill any extent recycled from a previous epoch.

### F-D10 (performance, minor) — Exports and imports hold the maintenance byte

[D §5b.6]: "Both directions run under the maintenance byte for file I/O and take the writer byte only to append commits". The maintenance byte is also what the hard-cap delta checkpoint of G10 needs; during a 10–25 s full export at 1e6 (or a 2–7 s import at 1e5) no checkpoint can run, the tail grows past 8× the threshold, and every CLI open replays a 32k+-op tail (30–40 ms, est.). Exports read only sealed segments and the log; they need no exclusion beyond "do not delete my inputs", which pins (G18) and the 60 s delete-pending grace already provide. **Fix:** G26.

### F-D11 (performance, minor; wording) — Merge folds and the change feed are O(store commits since LCA)

[D §5a.7 step 2]: "walking the commits on each side **sequentially through `log`/`hist`** (not per-node chain reads …)". Sequential reading of one interleaved log means the fold reads every branch's commits in the LCA..tip range and keeps two. At 1k commits/day a 14-day lane's merge scans ~14k commits ≈ 5–10 ms (est.) — fine, and still better than B's random chain reads ([21 §3.2 item 10]); but the cost is O(store commits since LCA), not O(the two sides), and [D §5a.11]'s "2k-op lane vs 5k trunk ops" understates it when 50 lanes write. G15's per-ref index makes both sides O(their own commits).

### F-D12 (RAM/perf, minor) — Leases keyed by `uid`; `HEADS` without expiry

[D §5d.1]: leases are "keyed by `uid`, never by branch" and `ready` "excludes nodes leased by another holder". `uid` is a cold 16-byte column; every lease check is then a binary search over the `UID` section (17 probes at 1e5, 2 MB mapped) instead of an O(1) `#N` probe. `ClientHead` keys include `session:<id>` ([D §5a.1]); the owner runs ~17 sessions with 401 runs [02 §5.1], so the `HEADS` table grows without a stated expiry. **Fix:** G27.

### F-D13 (performance, minor) — Ancestry through the own pack reader over the project repo

[D §5c]: `stale` "use[s] the same reader over the project repo's commit objects when present (loose + pack reader …), with the shared lazy-fact cache of [C §4.7]". Without a commit-graph, an `is-ancestor` walk inflates commit objects from packs at ~20–50 µs each (est.); the owner's repo has 1,882 commits [01 §7], so a cold walk is ~20–50 ms — no spawn, comparable to `git --version` alone, and cached thereafter. D also states no multi-pack-index support ("linear over `.idx` files"); a repository with 44 worktrees fetching produces several packs, still bounded. **Fix:** G27 — read `objects/info/commit-graph` generation numbers when present (git writes it by default since 2.24 on `gc`), which makes the walk O(1) per pair after a 2–4 MB map.

### Crash-and-kill behaviour of the new layers (checked, no finding)

Fork: `RefUpdate` + `Pin` in one flushed group; a kill before the `HEAD` write is recovered by the next writer's scan-adopt-republish (G2), provided GC reads pins only after that republish (G18 should state it). Promotion: written under the maintenance byte to a temp name, orphan swept (G14); the branch view is unchanged until the `RefUpdate` that moves `base_pin`. Merge/`sync`: one durable commit; staging ref moves in the same group. Export: temp objects/pack orphaned on a kill (git ignores `tmp_*`; must be swept by `image gc`); refs move before `gitmap` is appended, so a kill in between leaves the CAS one step ahead — D's "someone moved the image ref" path recovers by import-and-remap, clunky but safe. Import: batches of 4,096 ops as durable commits; resume from `gitmap`. Idle CPU: no timers in any mode; `watch` is leader-only. mmap: no mapped writes; `gitmap` sealed pages plus tail records. Locks: G1 blocking wait, diagnostics outside locked bytes. Renames: none on the commit path; image path renames covered by F-D6. fsync: one flush per durable commit, fatal on error, zero-filled extents. Torn writes: 32 B record header with LSN, epoch and xxh3; two `HEAD` slots (size fixed by G18).

### Score rationale

**7.5.** D is the best design on this lens because its engine is the revision-1 winner with the grafts made mandatory, and it is the only proposal that meets R1–R3. It loses 2.5 points for costs it does not price: two format-level defects that must be fixed before M1 (F-D1 overlay scan, F-D3 slot/pin arithmetic), one history-growth design choice (F-D2 `sync` copies), one RAM gate that its own workload breaks (F-D4), and an image writer whose Windows hygiene stops at the ref file (F-D6/F-D7). With G15–G26 applied, nothing in D's structure would need to change, and its measured-input budgets on `main` are the same as B's.
