# Глоссарий

Все термины, которые книга определяет или на которые ссылается, в алфавитном порядке; термины, которые пишутся латиницей, идут первыми. В каждой статье есть краткое определение и ссылка на главу, где термин важен. Термины, набранные как `code`, вводятся в командах, запросах или файлах ровно так, как показано.

Некоторые термины относятся не к продукту, а к тому, как строится сам проект, например юнит, уровень или «сначала красный»; в их статьях это сказано.

## Термины {#terms}

`#N` (короткий id) {#term-n-id}
: Короткий номер узла, который вы видите и вводите, например `#812`. Хранилище выделяет его по возрастанию и никогда не использует повторно, и на всех ветках он означает один и тот же узел. В командной строке его пишут без `#`, потому что `#` без кавычек в распространённых оболочках начинает комментарий. См. [Узлы и их id](concepts.html#nodes-and-ids).

`applies_to` {#term-applies-to}
: Поле правил и заметок, которое говорит, где они применяются: список ролей, фаз, линий и путей файлов, например `role:tester` или `path:src/net/**`. Пустой список означает «везде». По этому полю контекст-пак отбирает для задачи правила и предупреждения об опасностях. См. [Правила, критические заметки и полномочия](concepts.html#rules-and-authority).

Bare-репозиторий (bare repository) {#term-bare-repository}
: Репозиторий git без рабочего дерева, только с собственными данными git. По умолчанию [git-образ](#term-git-image) пишется в отдельный bare-репозиторий рядом с проектом, например `/work/tinyhttp-moirai.git`. См. [Куда попадает образ](git-image.html#destination).

BLAKE3 {#term-blake3}
: Быстрая криптографическая хэш-функция. Id коммита Moirai — это хэш BLAKE3-256 от [канонической формы](#term-canonical-form) коммита, а длинные текстовые тела адресуются 128-битным хэшем BLAKE3. См. [Адресация по содержимому](engine.html#content-addressing).

Bundle-файл (bundle) {#term-bundle}
: Один файл в формате bundle git, который содержит коммиты и ref. `moirai image export` и `image import` могут писать в bundle-файл и читать из него вместо репозитория, причём без установленного git. См. [Экспорт, импорт, push и pull](git-image.html#export-import).

CAS-условие (CAS guard) {#term-cas-guard}
: Охранное условие compare-and-set: условие, которое запись проверяет по вершине ветки, на которую она ляжет, в одном шаге с самой записью, например ожидаемая ревизия, статус или держатель аренды (`--if-rev`, `--if-status`, `--if-holder`). Если условие не выполнено, ничего не записывается (код выхода 4). См. [Запись, проигравшая гонку](tour.html#guarded-write).

diff3 {#term-diff3}
: Построчное трёхстороннее слияние текста относительно общего базового текста. Moirai использует его для текстовых полей и тел; если обе стороны изменили одни и те же строки, результатом становится [конфликтное значение](#term-conflict-value) `TextHunk`. См. [Типизированное трёхстороннее слияние](versions.html#merge).

`DRY` {#term-dry}
: Ключевое слово блока записи Lachesis: оно выполняет все проверки, не беря блокировку писателя, и печатает изменения, которые были бы сделаны, и дайджест множества целей. Применение того же блока с `IF TARGETS` и этим дайджестом даёт схему «спланировать, затем применить». У команд вроде `moirai rm` та же идея выражена флагом `--dry-run`. См. [Запись: один блок TX — один коммит](lachesis.html#writes).

`EXPECT` {#term-expect}
: Конструкция, обязательная для каждой цели `MATCH` в блоке записи Lachesis: сколько узлов цель должна найти — точное число или диапазон. Под блокировкой писателя она проверяется ещё раз; при несовпадении ничего не записывается, и команда завершается с кодом 4. См. [Запись: один блок TX — один коммит](lachesis.html#writes).

Fencing-токен (fencing token) {#term-fencing-token}
: Число из общего для хранилища счётчика, который только растёт; его несёт каждая [аренда](#term-lease). Завершение задачи, запись под её арендой и освобождение аренды предъявляют этот токен, поэтому агент, чья аренда истекла и перешла к другому, не может перезаписать работу нового держателя: его запись отвергается с кодом выхода 5. См. [Аренды и захваты](concepts.html#leases).

`format-v1` {#term-format-v1}
: Тег git, который заморозит версию 1 формата на диске. Он завершит веху M0 и откроет M1 — движок хранения; после него любое изменение замороженного байта снова открывает M0. Этого тега пока нет. См. [Ревью и именованные пробелы](building.html#reviews-and-holes).

Git-образ (git image) {#term-git-image}
: Копия всего графа и его истории, записанная в репозиторий git в виде текста: один [файл `.moi`](#term-moi-file) на узел и один коммит git на каждый коммит Moirai или на каждый [чекпоинт](#term-checkpoint). Любой инструмент git может его читать и переносить, а Moirai может импортировать его обратно, включая правки, сделанные через git; источником истины остаётся хранилище. См. [Сохранение в git](git-image.html).

gitmap {#term-gitmap}
: Таблица в хранилище, которая записывает, каким коммитом git стал каждый коммит Moirai, — отдельно для каждого места назначения и формата объектов. Её можно восстановить из образа, прочитав трейлеры `Klotho-Commit`. См. [Экспорт, импорт, push и pull](git-image.html#export-import).

HEAD клиента (HEAD of a client) {#term-head}
: Ветка, которую клиент читает и в которую пишет. Клиент — это каталог, именованный клиент или сессия агента, и у каждого свой HEAD, поэтому много агентов могут одновременно работать на разных ветках одного хранилища; перемещает его `moirai checkout`. Не путайте с [файлом `HEAD`](#term-head-slot) хранилища. См. [Много агентов, одно хранилище](versions.html#heads).

Kill-цикл (kill loop) {#term-kill-loop}
: Тест, который запускает настоящие процессы писателей и читателей на Windows и убивает их в случайных точках, приостанавливает или сдвигает часы — по 10 000 итераций на вариант. Ни один подтверждённый коммит не должен потеряться. См. [Направление тестирования](building.html#test-workstream).

Klotho {#term-klotho}
: Движок хранения внутри Moirai: библиотека, скомпилированная в единственный бинарник `moirai` и написанная с нуля на Rust. Он хранит версионированный граф на локальном диске и позволяет многим процессам читать и писать его без сервера. Git-образ использует его имя, например в `.klotho-image` и в трейлерах `Klotho-*`. См. [Под капотом: Klotho](engine.html).

Lachesis {#term-lachesis}
: Собственный язык запросов Moirai (LQ, файлы `*.lq`) в стиле Cypher. Каждая команда чтения — это [именованный запрос](#term-named-query) на нём, а каждая команда записи — [именованная мутация](#term-named-mutation). Язык назван по имени мойры, которая отмеряет нить. См. [Lachesis, язык запросов](lachesis.html).

LQ {#term-lq}
: Сокращённое название [Lachesis](#term-lachesis), языка запросов.

LQ-Bench {#term-lq-bench}
: Постоянный бенчмарк, который проверяет, пишет ли модель правильный Lachesis, получив только короткую [карточку skill](#term-skill-card). Он запускает модель на синтетическом хранилище со 150 вопросами в трёх формулировках и 40 заданиями, нацеленными на известные ловушки, а язык замораживается, только когда выполнены его гейты точности. См. [LQ-Bench](lachesis.html#lq-bench).

MCP {#term-mcp}
: Model Context Protocol — открытый протокол, через который харнесс даёт AI-агенту доступ к инструментам. Moirai предлагает [MCP-сервер](#term-mcp-server) для агентов и харнессов, у которых нет оболочки. См. [MCP-сервер](agents.html#mcp-server).

MCP-сервер (MCP server) {#term-mcp-server}
: `moirai mcp`: тот же бинарник в долгоживущем режиме, который харнесс запускает на одну сессию агента. Он говорит по MCP через stdio и предлагает десять инструментов, например `brief`, `pack`, `query`, `claim`, `complete` и `write`; для хранилища это просто ещё один клиент. См. [MCP-сервер](agents.html#mcp-server).

Moirai {#term-moirai}
: Продукт: версионированная графовая база данных для AI-агентов, пишущих код, и её единственная команда `moirai`. В греческой мифологии мойры — три богини судьбы; движок, [Klotho](#term-klotho), и язык запросов, [Lachesis](#term-lachesis), названы в честь двух из них. См. [главную страницу](index.html) и [Зачем нужна Moirai](why.html).

`proposed` {#term-proposed}
: Статус, с которого начинаются правила и решения и в котором текст из конвейера агентов попадает в хранилище. Предложенную запись агенты видят с пометкой `~proposed`, а действующей она становится только после явной смены статуса — обычно её делает оркестратор, просмотрев `moirai q proposed`. См. [Записываем правило, заметку и решение](tour.html#record-knowledge).

`ready` {#term-ready}
: [Производное состояние](#term-derived-state) задачи, которую агент может начать прямо сейчас: она [не заблокирована](#term-unblocked), никакой другой агент не держит на неё аренду, её не завершила и не удалила другая ветка, изменение которой эта ветка ещё не получила, и срок её отсрочки истёк. Это состояние существует только на вершине ветки, потому что аренды — живое состояние. См. [Производное состояние](concepts.html#derived-state).

`ready_to_close` {#term-ready-to-close}
: [Производное состояние](#term-derived-state) [контейнера](#term-container), все подзадачи которого завершены. См. [Производное состояние](concepts.html#derived-state).

Reflog {#term-reflog}
: Список всех перемещений указателя ветки — с тем, кто и зачем его переместил. `moirai reflog REF` печатает его, `undo` работает на его основе, а сборка мусора по умолчанию хранит его записи 90 дней. См. [История](versions.html#history).

`result.v1` {#term-result-v1}
: Строгий JSON-объект, которым заканчивает работу диспетчеризованный воркер: его задача, аренда, исход, сводка, доказательства и id записей, которые он сделал, плюс находки или заметки, которые он не смог записать сам. `moirai apply` читает эти объекты оттуда, где их оставил харнесс. См. [Диспетчерский паттерн](agents.html#dispatcher).

`rev` {#term-rev}
: Номер ревизии в заголовке результата, например `rev 5`: общий для хранилища порядковый номер коммита, из которого прочитан результат. Запись печатает `rev 4 -> 5`. Поскольку номер общий для всего хранилища, ревизии одной ветки могут идти с пропусками. См. [Проект](tour.html#the-project).

Rollup {#term-rollup}
: Два значения. В графе rollup — это счётчики прямых подзадач задачи и того, сколько из них завершено. В движке rollup записывает новый базовый сегмент, когда дельта-сегменты превышают четверть его размера; он выполняется только в отдельном процессе `moirai gc`. См. [Производное состояние](concepts.html#derived-state) и [Чекпоинты, rollup и сборка мусора](engine.html#maintenance).

Skill (навык) {#term-skill}
: Короткий файл с инструкциями, который учит агента пользоваться инструментом. Moirai поставляет три: основной skill `moirai` (не больше 800 токенов), `moirai-orchestrate` для оркестратора и `moirai-ql` — карточку Lachesis. См. [Skills](agents.html#skills).

`suspect` {#term-suspect}
: [Производное состояние](#term-derived-state) узла, построенного на чём-то, что изменилось: источник, из которого он выведен, который он цитирует или реализует, отозван, заменён или удалён, либо удалён файл, на который он ссылается. См. [Производное состояние](concepts.html#derived-state).

uid {#term-uid}
: Постоянная 128-битная идентичность узла; для большинства видов она случайная и записывается 32 шестнадцатеричными цифрами. Её используют хэши коммитов и git-образ, потому что она не меняется, когда данные переезжают в другое хранилище. См. [Узлы и их id](concepts.html#nodes-and-ids).

`unblocked` {#term-unblocked}
: [Производное состояние](#term-derived-state) открытой задачи, которая не является контейнером, не держит неразрешённого конфликта, не имеет ни незавершённых блокеров, ни предка, которого держит блокер извне его поддерева, и срок отсрочки которой на момент представления истёк. В отличие от [ready](#term-ready), это состояние действует на любой версии, в том числе в прошлом. См. [Производное состояние](concepts.html#derived-state).

Полномочия (authority) {#term-authority}
: Поле, которое говорит, кто стоит за утверждением: `owner`, `orchestrator`, `measured`, `research` или `agent`. Контекст-паки упорядочивают правила по [критичности](#term-criticality), затем по полномочиям, а правило с полномочиями владельца должно цитировать собственные слова владельца. См. [Правила, критические заметки и полномочия](concepts.html#rules-and-authority).

Авторская роль (author role) {#term-author-role}
: В собственном процессе разработки проекта — роль, которой принадлежит фиксированный набор путей в репозитории, например автор эталонной модели или тестовых фикстур. Правила разделения определяют, кто что может писать и кто что не должен читать; например, автор модели никогда не читает код движка. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Адресация по содержимому (content addressing) {#term-content-addressing}
: Именование данных по хэшу их содержимого. Id коммита Moirai — это хэш [BLAKE3](#term-blake3) канонической формы коммита, поэтому два хранилища с одним и тем же коммитом вычисляют один и тот же id, а одинаковое текстовое тело хранится только один раз. См. [Адресация по содержимому](engine.html#content-addressing).

Алиас (alias) {#term-alias}
: Прежний путь [файлового узла](#term-file-node). Алиас по-прежнему разрешает старые упоминания перемещённого файла, но никогда не захватывает новый файл по этому пути. Это слово встречается также в термине [обратный алиас](#term-reverse-alias) и в карте алиасов побочного ref git-образа. См. [Файловые узлы сохраняют идентичность](file-links.html#file-identity).

Аренда (lease) {#term-lease}
: Запись, которая говорит: «этот держатель сейчас работает над этим узлом» или «этот держатель действует в этой роли». Права на запись даёт только аренда, которую предъявляет вызывающий. Аренда живёт на уровне хранилища, поэтому её видит каждая ветка, и она никогда не сливается и не экспортируется. Задача, которую агент взял для себя, по умолчанию арендуется на 15 минут; аренду продлевает запись, которая предъявляет её, когда прошло больше половины этого времени. См. [Аренды и захваты](concepts.html#leases) и [Аренды и роли](agents.html#leases-and-roles).

База слияния (merge base) {#term-merge-base}
: Самый новый коммит, общий для двух веток. [Трёхстороннее слияние](#term-three-way-merge) сравнивает с ним каждую сторону. Поскольку слияния в `main` сначала выполняют синхронизацию, в повседневной работе база слияния одна. См. [Типизированное трёхстороннее слияние](versions.html#merge).

Байт сброса (flush byte) {#term-flush-byte}
: Второй байт блокировки в [файле `LOCK`](#term-lock-file) хранилища, используемый для [группового коммита](#term-group-commit). Писатель, который его берёт, один раз сбрасывает журнал на диск, и этот сброс покрывает все группы, дописанные до его начала. См. [Один сброс на многих писателей](engine.html#group-commit).

Блок `TX` (TX block) {#term-tx-block}
: Запись на Lachesis в форме `TX [ON branch] [KEY k] [IF TIP c] [LEASE L] { ... }`. Один блок — это один коммит на одной ветке, по принципу «всё или ничего», а его охранные условия, такие как [`EXPECT`](#term-expect), решают, ляжет ли он. См. [Запись: один блок TX — один коммит](lachesis.html#writes).

Блокер (blocker) {#term-blocker}
: Задача или вопрос, которые нужно завершить до начала другой задачи: источник ребра `blocks`. Удалённый блокер никогда молча ничего не разблокирует: его ребро остаётся как [помеченное ребро](#term-flagged-edge). «Блокер» — это ещё и самое серьёзное значение поля находки `severity` (`blocker`, `important`, `optional`), которое используют и ревью спецификации в самом проекте. См. [Рёбра](concepts.html#edges).

Блокировка писателя (writer lock) {#term-writer-lock}
: Эксклюзивная блокировка одного байта в файле `LOCK` хранилища. Её держит не больше одного процесса, и только для того, чтобы проверить и дописать подготовленный коммит; ожидающий писатель по умолчанию сдаётся через 2 секунды и называет процесс, который держит блокировку. Читатели её никогда не берут. См. [Много процессов, ни одного сервера](engine.html#process-model).

Бриф (brief) {#term-brief}
: Сводка всего хранилища для начала сессии: живые линии и аренды, идущие прогоны, открытые вопросы, критические правила, новые вердикты, битые файловые ссылки и число записей, ждущих ревью, — по умолчанию в пределах 8 000 байт. С хуками бриф попадает к агенту до его первого хода; без них первый вызов агента — `moirai brief`. См. [Контекст-паки и брифы](agents.html#packs-and-briefs).

Бюджет (budget) {#term-budget}
: Фиксированный предел. Moirai использует это слово в трёх смыслах: бюджеты производительности — проектные цели, например не больше 5 мс на команду чтения; байтовые бюджеты на то, что попадает в контекст агента, например на пак или ошибку; и счётные бюджеты, которые ограничивают работу одного запроса Lachesis. См. [Бюджеты](engine.html#budgets) и [Бюджеты и код выхода 10](lachesis.html#budgets).

Ветка (branch) {#term-branch}
: Именованная линия истории всего графа. Каждый узел, поле, ребро, тело и сама схема версионируются по веткам; `main` — обычная ветка, которую нельзя удалить, а остальные имена принадлежат семействам, таким как `lane/`, `plan/` и `tags/`. Ветки Moirai — её собственные, и они никогда не создаются из-за веток git. См. [Ветки и refs](versions.html#branches).

Веха (milestone) {#term-milestone}
: Один из двенадцати этапов, M0–M11, на которых Moirai строится в порядке зависимостей. Следующая веха опирается на предыдущую только после того, как та завершена и все её гейты зелёные. Проект находится в M0. См. [Дорожная карта](building.html#roadmap).

Взять задачу, захват (claim) {#term-claim}
: Взять задачу в работу: `moirai claim ID` или инструмент MCP `claim` создаёт на задачу [аренду](#term-lease). Задача должна быть живой и готовой к работе на ветке того, кто её берёт. Сам захват статус не меняет; в `in_progress` задачу переводит флаг `--start` или первая запись под арендой. См. [Аренды и захваты](concepts.html#leases).

Вид узла (kind) {#term-kind}
: Тип узла. В основной схеме тринадцать видов, например `task`, `rule`, `decision`, `finding` и `artifact`, и проект может добавлять свои. У каждого вида свои поля и статусы. См. [Виды узлов](concepts.html#kinds).

Виртуальное поле `done` (virtual done) {#term-virtual-done}
: Логическое поле `done` у задач, вопросов и вердиктов, которое не хранится, а читается из статуса. Запись `done = true` выполняет переход статуса со всеми его проверками, поэтому один и тот же факт никогда не хранится дважды. См. [Виртуальное поле done](concepts.html#virtual-done).

Воркер (worker) {#term-worker}
: Агент, которого оркестратор запускает для одной задачи в одной роли, например разработчика или тестировщика. Диспетчеризованный воркер при старте получает [ролевой пак](#term-role-pack), записывает свою работу напрямую и заканчивает объектом [`result.v1`](#term-result-v1). См. [Диспетчерский паттерн](agents.html#dispatcher).

Встроенная функция (built-in) {#term-built-in}
: Свойство или функция Lachesis, которые открывают собственное состояние движка, например `t.ready`, `t.unblocked`, `subtree(n)`, `blockers()` или `link_state()`. Встроенные функции делят код с путём записи, поэтому запрос и команда не могут разойтись в том, что означает одно и то же слово. См. [Состояние движка во встроенных функциях](lachesis.html#built-ins).

Вывод истории в архив (history retirement) {#term-history-retirement}
: Обслуживание, которое сжимает заполненный экстент журнала в файл `hist` с индексом коммитов. По умолчанию ничего не удаляется. См. [Чекпоинты, rollup и сборка мусора](engine.html#maintenance).

Гейт (gate) {#term-gate}
: Тест, который падает, когда цель не достигнута или нарушено правило, например перебор точек краша, бюджет времени или бенчмарк точности запросов. Каждый гейт становится обязательным на какой-то вехе и остаётся обязательным дальше; проваленный гейт блокирует выход из своей вехи и из всех последующих. См. [Гейты простыми словами](building.html#gate-catalogue).

Групповой коммит (group commit) {#term-group-commit}
: Один сброс на диск, общий для многих писателей. В Klotho ему не нужен лидер: писатель, чьи записи ещё не долговечны, берёт [байт сброса](#term-flush-byte) и один раз сбрасывает журнал для всех групп, дописанных до начала его сброса. Проектная цель для всплеска из шестнадцати писателей — не больше трёх сбросов. См. [Один сброс на многих писателей](engine.html#group-commit).

Дерево-писатель (writer tree) {#term-writer-tree}
: Единственное рабочее дерево, наблюдения которого могут перепривязывать файловые ссылки ветки: [назначенное дерево](#term-designated-tree) ветки, пока его HEAD в git находится на линии истории git, соответствующей ветке. Все остальные деревья — [деревья-читатели](#term-reader-tree). См. [Закрепление](file-links.html#settling).

Дерево-читатель (reader tree) {#term-reader-tree}
: Любое рабочее дерево, кроме [дерева-писателя](#term-writer-tree) ветки. Оно разрешает и показывает состояния ссылок, но его наблюдения ждут в виде отложенных строк, пока дерево-писатель не увидит то же перемещение. См. [Закрепление](file-links.html#settling).

Диспетчер (dispatcher) {#term-dispatcher}
: Паттерн, по которому оркестратор запускает много воркеров: открыть [прогон](#term-run), массово взять задачи в виде аренд в рамках прогона, запустить каждого воркера со строкой-маркером в промпте и применить все результаты одним шагом через `moirai apply`. Повторный запуск после сбоя сходится к тому же результату, а не повторяет работу. См. [Диспетчерский паттерн](agents.html#dispatcher).

Дифференциальное тестирование (differential testing) {#term-differential-testing}
: Прогон одних и тех же входов через две независимые реализации и сравнение результатов. Движок сравнивается с [эталонной моделью](#term-reference-model) — не меньше миллиона команд на веху, а каждый экспортированный образ проверяется утилитой командной строки git. См. [Направление тестирования](building.html#test-workstream).

Длительный прогон (soak) {#term-soak}
: Долгий тест под смешанной нагрузкой. Релизный гейт требует 72 часов смешанной нагрузки с kill-циклами на разных ветках без единого потерянного подтверждённого коммита. См. [Релизный гейт](building.html#release-gate).

Доказательство (evidence) {#term-evidence}
: То, по чему Moirai находит перемещённый файл. Точное доказательство — например тот же file id с тем же размером и временем изменения, записанное намерение `file mv` или переименование git внутри одного коммита — может [перепривязать](#term-re-bind) ссылку автоматически; более слабое, например похожее содержимое, только предлагает кандидата. Доказательства показывает `moirai file where ID --evidence`. См. [Как ссылка следует за файлом при перемещении и правке](file-links.html#following-a-move).

Единица fs (fs unit) {#term-fs-unit}
: Счётная единица работы с файловой системой, которая ограничивает, сколько чтение может сделать для вычисления состояний ссылок (по умолчанию 400 на запрос). Подсчёт единиц вместо времени гарантирует, что при одном и том же состоянии дерева чтение всегда останавливается на одной и той же ссылке; ссылки, до которых оно не дошло, показывают `unverified (budget)`. См. [Бюджеты времени](file-links.html#time-budgets).

Единица работы (work unit) {#term-work-unit}
: Счётная единица работы запроса, например одна просмотренная строка или одно развёрнутое ребро. Запрос Lachesis по умолчанию может потратить 2 000 000 единиц; подсчёт вместо замера времени гарантирует, что один и тот же запрос на одной и той же версии всегда останавливается на одной и той же строке. См. [Бюджеты и код выхода 10](lachesis.html#budgets).

Журнал операций (log) {#term-log}
: Журнал хранилища, в который только дописываются все изменения, — записи с контрольными суммами и 32-байтовыми заголовками. Это каноническая история, и ничто в нём не переписывается на месте; текущее состояние строится из него в [сегменты](#term-segment). См. [История в журнале, текущее состояние в сегментах](engine.html#log-and-segments).

Заблокирована (blocked) {#term-blocked}
: [Производное состояние](#term-derived-state) незавершённой задачи, у которой есть незавершённый [блокер](#term-blocker) — собственный или унаследованный от предка. `moirai tree` помечает такие задачи `BLOCKED`. См. [Производное состояние](concepts.html#derived-state).

Закрепление (settle) {#term-settle}
: Запись новых мест перемещённых файлов в версионированную историю. Чтения лишь показывают, где файл находится сейчас; закрепление записывает точные [перепривязки](#term-re-bind), которые допускают его строгие правила. См. [Закрепление](file-links.html#settling).

Заложенная ошибка (seeded bug) {#term-seeded-bug}
: Намеренная ошибка, заложенная, чтобы доказать, что тестовый стенд её находит. В [игрушечном журнале](#term-toy-log) есть переключаемые заложенные ошибки, которые должен найти перебор точек краша, а автор, который их закладывает, никогда не пишет сам перебор. См. [Направление тестирования](building.html#test-workstream).

Запечатанный файл (sealed file) {#term-sealed-file}
: Файл хранилища, который записывается один раз, делается долговечным, помечается только для чтения и больше никогда не меняется, например сегмент. В память отображаются только запечатанные файлы. См. [Файлы хранилища](engine.html#store-files).

Запись намерения (intent record) {#term-intent-record}
: Долговечная запись, которую `moirai file mv` или `file rm` дописывает в журнал, прежде чем трогать файловую систему. После сбоя следующий писатель или `moirai doctor` по ней завершает перемещение или отменяет его. См. [Явные глаголы](file-links.html#explicit-verbs).

Игрушечный журнал (toy log) {#term-toy-log}
: Небольшая тестовая реализация протокола коммита с переключаемыми [заложенными ошибками](#term-seeded-bug); на ней показывают, что перебор точек краша находит каждую из них, ещё до появления настоящего движка. См. [Направление тестирования](building.html#test-workstream).

Именованная мутация (named mutation) {#term-named-mutation}
: Сохранённая именованная запись на Lachesis, которая вызывается как `tx.<name>`. Каждая команда записи CLI — такая мутация: `moirai claim` выполняет `tx.claim`, а `--show-tx` печатает блок записи, стоящий за командой. См. [Именованные запросы и мутации](lachesis.html#named-queries).

Именованный запрос (named query) {#term-named-query}
: Сохранённый именованный запрос Lachesis с типизированными параметрами. Каждая команда чтения — такой запрос из встроенной библиотеки `std`, поэтому `moirai ready` — то же самое, что `moirai q ready`. Проект может определять собственные запросы, и они версионируются, как и вся остальная схема. См. [Именованные запросы и мутации](lachesis.html#named-queries).

Именованный пробел (named hole) {#term-named-hole}
: Значение в спецификации, которое может установить только замер; оно записывается как `HOLE(<id>)` и внесено в индекс вместе с кандидатами и замером, который его решает. Пример — число операций журнала, после которого запускается чекпоинт. См. [Ревью и именованные пробелы](building.html#reviews-and-holes).

Индекс покрытия (coverage index) {#term-coverage-index}
: Файл спецификации, который сопоставляет каждому замороженному пункту разделы, где он описан, фикстуры, которые его проверяют, и функцию эталонной модели, которая его реализует. См. [Ревью и именованные пробелы](building.html#reviews-and-holes).

Историческое ребро (historical edge) {#term-historical-edge}
: Ребро, которое записывает, откуда что-то взялось или о чём оно, например `supersedes`, `cites` или `mentions`. Оно может и дальше указывать на удалённый узел, который тогда показывается как [надгробие](#term-tombstone). См. [Рёбра](concepts.html#edges).

Каноническая форма (canonical form) {#term-canonical-form}
: Заданная спецификацией последовательность байтов для фрагмента данных, чтобы любая реализация записывала для одного и того же содержимого ровно одни и те же байты. Каноническая форма коммита охватывает его вид, родителей, значение часов, автора, контекст git, сообщение и изменения, а её хэш и есть id коммита; файлы узлов git-образа — тоже канонический текст. См. [Адресация по содержимому](engine.html#content-addressing).

Карточка skill (skill card) {#term-skill-card}
: Короткий справочник, по которому агенты учат Lachesis, — не больше 1 000 токенов и 3 500 байт; поставляется как skill `moirai-ql`. [LQ-Bench](#term-lq-bench) измеряет, достаточно ли его. См. [LQ-Bench](lachesis.html#lq-bench).

Квантифицированный путь (quantified path) {#term-quantified-path}
: Паттерн Lachesis, который повторяет ребро, — в написании Cypher (`-[:CHILD_OF*1..2]->`) или GQL (`-[:CHILD_OF]->{1,2}`). Вычисление идёт уровень за уровнем с множеством посещённых узлов, поэтому любой квантифицированный паттерн завершается. См. [Квантифицированные пути](lachesis.html#quantified-paths).

Класс долговечности (durability class) {#term-durability-class}
: Уровень защиты, который получает на диске запись определённого рода: `durable` (подтверждается только после покрывающего её сброса; так пишется любое изменение графа), `lazy` (сигналы жизни, курсоры чтения и подобные записи, которые может потерять отключение питания) и два класса для размеров файлов и записей каталогов. Если место не может обеспечить класс, хранилище в нём не допускается. См. [Классы долговечности и тихий режим](engine.html#durability).

Ключ идемпотентности (idempotency key) {#term-idempotency-key}
: Ключ, который делает запись безопасной для повтора. Ключ привязан к канонической форме записи со значениями её параметров (форматирование, написание и имена переменных не важны) и к её ветке: повтор с тем же ключом и той же записью возвращает исходный результат, а тот же ключ с другой записью завершается с кодом 9. Ключ есть у каждой записи через MCP. См. [Коды выхода](agents.html#exit-codes).

Контейнер (container) {#term-container}
: Задача, у которой есть подзадачи. Контейнер сам по себе никогда не бывает готов к работе, поэтому ни один агент не получает его напрямую; он [готов к закрытию](#term-ready-to-close), когда все его подзадачи завершены. См. [Производное состояние](concepts.html#derived-state).

Контекст-пак (context pack) {#term-context-pack}
: Контекст, который Moirai вычисляет для одной задачи и одной роли: применимые правила, задача с предками и критериями приёмки, относящиеся к делу разделы плана, находки, замеры, заметки с областью действия и недавние изменения — всё это укладывается в байтовый бюджет роли (предварительно 16 000 байт для разработчика). Записи сокращаются раньше, чем что-либо отбрасывается, а всё отброшенное подсчитывается в первой и последней строке вместе с командой, которая это получит. См. [Контекст-паки и брифы](agents.html#packs-and-briefs).

Конфликтное значение (conflict value) {#term-conflict-value}
: То, что слияние сохраняет для ключа, когда его правило не может решить, например когда обе ветки задали полю разные значения: класс конфликта и три стороны — `base`, `ours` и `theirs`. Слияние всё равно проходит; узел помечается как [конфликтный](#term-conflicted) и покидает очередь готовых задач, пока кто-нибудь не выполнит `moirai resolve`. См. [Конфликты хранятся как данные](versions.html#conflicts).

Конфликтный (conflicted) {#term-conflicted}
: [Производное состояние](#term-derived-state) узла, который держит на этой ветке неразрешённое [конфликтное значение](#term-conflict-value). Конфликтная задача покидает очередь готовых задач, пока конфликт не разрешён. См. [Производное состояние](concepts.html#derived-state).

Критичность (criticality) {#term-criticality}
: Поле со значениями `critical`, `high`, `normal` и `low`. Заметка или правило с пометкой `critical` показывается первым в каждом брифе и контекст-паке, и всегда полным текстом. См. [Правила, критические заметки и полномочия](concepts.html#rules-and-authority).

Курсор (cursor) {#term-cursor}
: Метка, которая говорит, где продолжить. Длинный результат Lachesis заканчивается курсором, который получает следующую страницу, а каждая сессия агента хранит курсор в [ленте изменений](#term-change-feed), чтобы хуки показывали только изменения с её последнего просмотра. См. [WHERE, RETURN, ORDER BY и LIMIT](lachesis.html#clauses).

Лента изменений (change feed) {#term-change-feed}
: Общий для хранилища список изменений, по строке на изменение: ревизия, ветка, узел, операция и кто её сделал, плюс события аренд и маркеров. Её читает `moirai changes --since N`, а хуки превращают её в короткий список относящихся к делу изменений перед каждым промптом; ничто её не рассылает и ничто её не опрашивает. См. [Лента изменений](concepts.html#change-feed).

Линия (lane) {#term-lane}
: Линия параллельной работы. В Moirai линия объединяет три вещи: ветку `lane/<name>`, [рабочее дерево](#term-worktree) git для кода и узел `lane` на `main`, который записывает и то и другое; все три настраивает `moirai lane open`. См. [Линии и рабочие деревья git](versions.html#lanes).

Маркер `deleted` (deleted marker) {#term-deleted-marker}
: Запись уровня хранилища, которая создаётся при удалении узла на ветке. Пока другая ветка не получила удаление, маркер исключает узел из очереди готовых задач, списков блокеров и захватов задач на этой ветке, поэтому ни одна линия не раздаёт работу, которую удалила другая линия. Также называется маркером удаления. См. [Координация между ветками](versions.html#coordination).

Маркер `~main` (~main marker) {#term-main-marker}
: Пометка критического правила, которое записано на `main`, но ещё не влито в текущую линию. Такое правило всё равно появляется в контекст-паках линии, поэтому ветвление никогда не прячет правило от агента. См. [Координация между ветками](versions.html#coordination).

Маркер `settled` (settled marker) {#term-settled-marker}
: Запись уровня хранилища, которая создаётся всякий раз, когда задача становится `done` или `cancelled` на любой ветке любым путём. Все остальные ветки после этого считают задачу завершённой, но ещё не влитой: взять её или выдать в работу там нельзя. Маркер перестаёт иметь значение, когда история этой ветки уже содержит завершение. См. [Координация между ветками](versions.html#coordination).

Маркер удаления (deletion marker) {#term-deletion-marker}
: Другое название [маркера `deleted`](#term-deleted-marker).

Машина состояний (status machine) {#term-status-machine}
: Список переходов статусов, которые допускает вид. Запись может выполнять только перечисленные переходы, и у некоторых из них есть [охранные условия](#term-guard). См. [Статусы и охраняемые переходы](concepts.html#statuses).

Многопроцессная симуляция (multi-process simulation) {#term-multi-process-simulation}
: Тест, который запускает много симулированных процессов с воспроизводимым по зерну (seeded) планированием и внедряет сбои, неудачные сбросы, запоздалые освобождения блокировок и скачки часов, пока [эталонная модель](#term-reference-model) проверяет каждое чтение. См. [Направление тестирования](building.html#test-workstream).

Модель сбоев (fault model) {#term-fault-model}
: Записанный список сбоев, которые должен переживать код хранения; в тестах его соблюдение обеспечивает симулированная файловая система: потерянные или разорванные несброшенные секторы, переименования, которые становятся долговечными только после синхронизации их каталога, неудачные сбросы, переполненный диск, приостановленные процессы и скачки часов. См. [Направление тестирования](building.html#test-workstream).

Мутационное тестирование (mutation testing) {#term-mutation-testing}
: Внесение в код небольших намеренных изменений — их называют мутантами — и проверка того, что тесты их ловят. На выходе из каждой вехи наборы тестов должны ловить не меньше 90 % мутантов в семантическом коде и каждую ошибку из каталога намеренных ошибок протокола. См. [Направление тестирования](building.html#test-workstream).

Надгробие (tombstone) {#term-tombstone}
: То, что остаётся от удалённого узла: его строка с пометкой об удалении, с видом, названием, удалившим коммитом, автором удаления, причиной и заменой. Его `#N` никогда не используется повторно, каждая ссылка на него показывает надгробие, а откат удалившего коммита возвращает узел. См. [Надгробия](concepts.html#tombstones).

Назначенное дерево (designated tree) {#term-designated-tree}
: Единственное рабочее дерево, сопоставленное ветке для файловых ссылок. У каждой ветки не больше одного назначенного дерева, и каждое дерево обслуживает не больше одной ветки: для линии это рабочее дерево, которое называет `moirai lane open`, для `main` его задаёт ключ конфигурации `files.main-tree`, а для любой другой ветки — `moirai worktree bind`. Пока HEAD дерева в git находится на линии истории git, соответствующей ветке, оно является [деревом-писателем](#term-writer-tree) ветки. См. [Закрепление](file-links.html#settling).

Намерение ссылки (link intent) {#term-link-intent}
: Версионируемый слой файловых ссылок: файловые узлы, якоря, рёбра `at`, намерение удаления и история перемещений каталогов. Он ветвится, сливается и переносится в git-образе, а [разрешение](#term-resolution) вычисляется отдельно в каждом рабочем дереве. См. [Рабочие деревья, ветки и git-образ](file-links.html#worktrees-and-branches).

Неблокирующий отказ (fail-open) {#term-fail-open}
: Такое устройство, при котором сбой не останавливает работу. Хуки Moirai устроены именно так: хук, который упал, вышел по тайм-ауту или не смог достучаться до Moirai, не останавливает агента, и контекст этого события просто отсутствует, но никогда не бывает неверным. См. [Хуки: необязательные ускорители](agents.html#hooks).

Обратный алиас (reverse alias) {#term-reverse-alias}
: Второе имя типа ребра в Lachesis, которое читает его в обратном направлении, например `BLOCKED_BY` для `BLOCKS`, чтобы вопрос можно было задать с любого конца. См. [Паттерны: виды, рёбра и направления](lachesis.html#patterns).

Общий каталог git (git common directory) {#term-git-common-directory}
: Каталог, общий для всех рабочих деревьев одного репозитория git, обычно каталог `.git` главного рабочего дерева. Moirai кладёт туда своё хранилище, в `<git-common-dir>/moirai/`, чтобы каждое рабочее дерево находило одно и то же хранилище. См. [Где лежит хранилище](engine.html#store-location).

Оверлей (overlay) {#term-overlay}
: Небольшая структура в памяти, в которую каждый процесс проигрывает [хвост](#term-tail) журнала — изменения, которых ещё нет ни в одном сегменте. Читатель сначала смотрит в оверлей, затем в дельта-сегменты от новых к старым, затем в базовый сегмент. См. [История в журнале, текущее состояние в сегментах](engine.html#log-and-segments).

Оракул формата (format oracle) {#term-format-oracle}
: Крейт только для тестов, который декодирует и заново кодирует каждую замороженную структуру на диске независимо от кода продукта, начиная с написанных вручную шестнадцатеричных фикстур. Его автор — не автор кодека продукта. См. [Эталонная модель](building.html#reference-model).

Оркестратор (orchestrator) {#term-orchestrator}
: Агент или человек, который планирует работу, распределяет воркеров по линиям, проводит ревью и сливает. В Moirai это ещё и роль: её сессионная аренда позволяет писать всё на любой ветке, включая команды веток, слияния, удаления и образа. См. [Аренды и роли](agents.html#leases-and-roles).

Основная ветка (trunk) {#term-trunk}
: В собственном процессе разработки проекта — главная линия репозитория кода, ветка `master`, в которую вливает только одна оркестрирующая сессия. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Отображение в память (memory mapping) {#term-memory-mapping}
: Возможность для процесса читать файл так, будто это память, прямо из [страничного кэша](#term-page-cache) операционной системы. Klotho отображает только [запечатанные файлы](#term-sealed-file) и только для чтения — отчасти потому, что на Windows размер отображённого файла нельзя изменить. См. [Файлы хранилища](engine.html#store-files).

Отсутствующее значение (absent value) {#term-absent-value}
: В Lachesis — значение необязательного поля, которое не задано. Lachesis использует двузначную логику: сравнение с отсутствующим значением ложно, а его отрицание истинно, поэтому `t.assignee <> 'dev#1'` возвращает и задачи без исполнителя. См. [Отсутствующее значение и двузначная логика](lachesis.html#absent-values).

Охранное условие (guard) {#term-guard}
: Условие, которое проверяется в момент записи. Охранные условия статусов входят в [машину состояний](#term-status-machine) вида; например, задача не может стать завершённой, пока не завершена её подзадача. [CAS-условия](#term-cas-guard) добавляет вызывающий, например `--if-status in_progress`. Невыполненное условие ничего не записывает и называет то, что помешало. См. [Статусы и охраняемые переходы](concepts.html#statuses).

Очередь готовых задач (ready queue) {#term-ready-queue}
: Список [готовых к работе](#term-ready) задач в фиксированном порядке (приоритет, затем id) — так, как его печатает `moirai ready` и как его выбирает `t.ready` в Lachesis. См. [Что можно начинать и что задерживает работу](tour.html#ready-and-blocking).

Пак (pack) {#term-pack}
: Сокращение от [контекст-пака](#term-context-pack); собирает его `moirai pack ID --role ROLE`. См. также [ролевой пак](#term-role-pack).

Пара концов (endpoint pair) {#term-endpoint-pair}
: То, что связывает паттерн пути переменной длины в Lachesis: одна строка на пару начального и конечного узлов, а не на каждый путь, потому что на графах, где есть рёбра в обход промежуточных узлов, число путей растёт взрывообразно. `count(*)` по такому паттерну считает пары концов, и об этом сообщает уведомление `N08`. См. [Подсчёт](lachesis.html#counting).

Перебор точек краша (crash-point enumeration) {#term-crash-point-enumeration}
: Тест, который внедряет краш в каждую точку записи, сброса и публикации кода хранения на симулированной файловой системе и перебирает все подмножества несброшенных секторов (когда их не больше 12) и все сочетания двух [слотов `HEAD`](#term-head-slot). После каждого краша восстановление должно сохранить каждый подтверждённый коммит. См. [Направление тестирования](building.html#test-workstream).

Перепривязка (re-bind) {#term-re-bind}
: Запись нового пути файлового узла в версионированную историю после перемещения. [Закрепление](#term-settle) перепривязывает автоматически — по умолчанию только по точному доказательству с единственным кандидатом и только из [дерева-писателя](#term-writer-tree) ветки. `links fix` записывает перепривязку, о которой кто-то принял решение; если у актора нет роли `owner`, она остаётся помеченной как догадка, пока её не подтвердят. См. [Закрепление](file-links.html#settling).

Песочница (sandbox) {#term-sandbox}
: Ограничение харнесса на то, что могут записывать команды агента. Чтениям доступ на запись никогда не нужен; отвергнутая запись подсказывает агенту другой способ её сделать, так что она откладывается, но не теряется. См. [Песочницы](agents.html#sandboxes).

Пин (pin) {#term-pin}
: Ссылка, которая сохраняет живым снимок файлов сегментов хранилища. Ответвление ветки, слияние в `main` и `moirai tag NAME --pin` — каждое из них фиксирует снимок, поэтому чтение этой точки остаётся быстрым, а сборка мусора её сохраняет. В файле `.moi` атрибут `pin=` на ребре цитирования фиксирует цитату за одним коммитом. См. [История](versions.html#history).

Побочное состояние (side state) {#term-side-state}
: Статус, который уводит в сторону от основной линии работы вида, например `deferred`, `cancelled` или `frozen` у задачи. См. [Статусы и охраняемые переходы](concepts.html#statuses).

Побочный ref (side ref) {#term-side-ref}
: Ref git в репозитории образа вне всех экспортированных веток, `refs/klotho/meta/<store-id>`, который хранит подсказки одного хранилища: его id, состояние экспорта и карту из uid в его короткие id. Он не входит в дерево ни одного коммита и не хэшируется. См. [Куда попадает образ](git-image.html#destination).

Помеченное ребро (flagged edge) {#term-flagged-edge}
: Ребро `blocks` или `gates`, источник которого удалён без замены. Ребро остаётся, получает пометку и держит зависимую задачу вне очереди готовых задач, пока кто-нибудь его не разрешит, поэтому удаление никогда молча не разблокирует работу. Помеченные рёбра переживают полный круг через git-образ. См. [Удаление](concepts.html#deletion).

Порядковый номер в журнале (LSN) {#term-log-sequence-number-lsn}
: Позиция записи в [журнале](#term-log), записанная в её заголовок. Запись действительна только на своей позиции. См. [История в журнале, текущее состояние в сегментах](engine.html#log-and-segments).

Представление (view) {#term-view}
: Картина графа на одной версии, доступная только для чтения. Простое имя ветки даёт живую вершину, где существуют аренды и готовность; тег, коммит или ревизия с суффиксом дают представление прошлого, где запись отвергается, а живое состояние недоступно. См. [Чтение прошлого](versions.html#reading-the-past).

Проверка тишины (quiescence) {#term-quiescence}
: Короткое ожидание перед записью перемещения. Закрепление повторно проверяет старый путь не раньше чем через 50 мс после того, как в последний раз видело его отсутствующим, и отменяет перепривязку, если файл вернулся, потому что редакторы, которые сохраняют атомарно, на несколько миллисекунд переименовывают оригинал. См. [Закрепление](file-links.html#settling).

Прогон (run) {#term-run}
: Один прогон агента или скриптового рабочего процесса, записанный как узел вида `run` с артефактами, которые он должен создать. [Диспетчер](#term-dispatcher) берёт задачи для всего прогона и применяет его результаты одной пачкой, а прогон закрывается зелёным, только если существует каждый ожидаемый артефакт. См. [Диспетчерский паттерн](agents.html#dispatcher).

Производное состояние (derived state) {#term-derived-state}
: Ответы, которые следуют из графа, а не из того, что кто-то записал, например [готовность](#term-ready), [заблокированность](#term-blocked), rollup-счётчики и [suspect](#term-suspect). Движок вычисляет каждый из них по единственному определению, общему для пути записи, каждой команды и Lachesis; ни один агент не может записать производное состояние, и git-образ его никогда не хранит. См. [Производное состояние](concepts.html#derived-state).

Происхождение (provenance) {#term-provenance}
: Запись о том, откуда пришло изменение. Каждое изменение принадлежит ровно одному коммиту, который записывает актора, его роль, сессию, ветку Moirai, git head, ветку git и рабочее дерево, в которых он работал, и сообщение. См. [Правила, критические заметки и полномочия](concepts.html#rules-and-authority).

Промежуточный ref (staging ref) {#term-staging-ref}
: Ref с именем `merge/<dst>/from/<src>` (или `import/<ref>` для импорта), на котором ждёт слияние, обнаружившее [структурное нарушение](#term-structural-violation). Ветка назначения не сдвигается; вы исправляете результат командой `moirai resolve` и завершаете слияние командой `moirai merge --continue`. См. [Структурные нарушения останавливают слияние](versions.html#violations).

Профиль модели (model profile) {#term-model-profile}
: Настройка для семейства моделей, которая записывает, насколько хорошо измерен Lachesis этой модели: `gated`, `compatible` или `unknown`. Модель с профилем `unknown` пишет только через именованные мутации, а модели, не прошедшие гейты бенчмарка, всегда видят [эхо чтения](#term-reading-echo). См. [LQ-Bench](lachesis.html#lq-bench).

Рабочее дерево (worktree) {#term-worktree}
: Рабочее дерево git. У одного репозитория git их может быть несколько, каждое на своей ветке, — так обычно и работают параллельные агенты. [Линия](#term-lane) Moirai привязывает одно рабочее дерево к одной ветке Moirai, а все рабочие деревья репозитория делят одно хранилище. См. [Линии и рабочие деревья git](versions.html#lanes).

Рабочее дерево гейта (gate worktree) {#term-gate-worktree}
: В собственном процессе разработки проекта — отдельное нейтральное рабочее дерево git, в котором полный гейт прогоняется на вершине ветки, прежде чем эту ветку можно будет влить в [основную ветку](#term-trunk). См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Разрешение (resolution) {#term-resolution}
: Два значения. Как поле — то, чем закончилась закрытая задача или находка: `completed`, `wontdo`, `duplicate`, `superseded`, `obsolete` или `rework`. Для файловых ссылок разрешение — это слой, вычисляемый отдельно в каждом рабочем дереве (состояния ссылок, file id, доказательства и предложения); он никогда не версионируется и не экспортируется. См. [Типизированные поля](concepts.html#fields) и [Рабочие деревья, ветки и git-образ](file-links.html#worktrees-and-branches).

Ребро (edge) {#term-edge}
: Типизированная направленная связь между двумя узлами, например `blocks` или `parent`. Одно и то же ребро между одними и теми же двумя узлами существует не больше одного раза, и Moirai хранит каждое ребро в обоих направлениях в одном коммите. В основной схеме 25 видов рёбер, каждый из которых либо [структурный](#term-structural-edge), либо [исторический](#term-historical-edge). См. [Рёбра](concepts.html#edges).

Ребро `at` {#term-at-edge}
: Вид ребра файловой ссылки: оно идёт от любого узла к [файловому узлу](#term-file-node) и несёт один или несколько [якорей](#term-anchor). См. [Что такое ссылка](file-links.html#what-a-link-is).

Ревизия (revision) {#term-revision}
: Имя точки в истории в стиле git: вершина ветки (`main`), префикс коммита, порядковый номер (`s4400`), предок (`main~3`), позиция или время в reflog (`main@2026-11-01`) или диапазон для `log` и `diff`. Команды чтения принимают `--at REV`, а запрос Lachesis может начинаться с `USE REV`. См. [Чтение прошлого](versions.html#reading-the-past).

Реестр токенов (token ledger) {#term-token-ledger}
: Часть набора тестов, которая записывает каждый байт, который Moirai помещает в контекст агента, отдельно для каждого харнесса и модели, считает его токенизатором этой модели и сверяет с бюджетами токенов. См. [Бюджеты](engine.html#budgets).

Релизный гейт (release gate) {#term-release-gate}
: Условия, при которых Moirai можно назвать выпущенной, то есть «завершённой и закалённой»: среди прочего, выход из каждой вехи со всеми её гейтами, выполнение каждого бюджета на трёх масштабах, чистые ночная симуляция и kill-циклы, 72-часовой длительный прогон и учения по резервному копированию, восстановлению и ремонту. См. [Релизный гейт](building.html#release-gate).

Родной коммит (native commit) {#term-native-commit}
: Коммит git в образе, трейлеры `Klotho-*` которого проходят проверку: Moirai восстанавливает по ним каноническую форму коммита, заново вычисляет хэш и убеждается, что он равен `Klotho-Commit`. Такой коммит импортируется со своим собственным id. См. [Правки, сделанные через git](git-image.html#foreign).

Ролевой пак (role pack) {#term-role-pack}
: Короткий пак не больше 3 000 байт, который хук выдаёт диспетчеризованному воркеру при старте: критические правила для его роли и команда `pack` для его задачи. Собственный пак воркера затем перечисляет эти правила одной строкой id. См. [Хуки: необязательные ускорители](agents.html#hooks).

Роль этапа (stage role) {#term-stage-role}
: В собственном процессе разработки проекта — работа, которую агент выполняет внутри [юнита](#term-unit): архитектор, критик архитектуры, разработчик, тестировщик, верификатор, ревьюер кода или механик. Обязанности разделены: разработчик никогда не выносит окончательный вердикт, а ревьюер никогда не исправляет то, что нашёл. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Сборка мусора (garbage collection) {#term-garbage-collection}
: `moirai gc` — отдельный процесс обслуживания. Он сохраняет всё, что достижимо из ветки, тега, [пина](#term-pin) или записи reflog моложе 90 дней, отбрасывает недостижимые коммиты старше 14 дней и удаляет старые файлы только после льготного периода. См. [Чекпоинты, rollup и сборка мусора](engine.html#maintenance).

Сегмент (segment) {#term-segment}
: Неизменяемый файл, отображаемый в память, который хранит текущее состояние графа по столбцам: заголовки узлов, поля, рёбра каждого узла в обоих направлениях и заранее вычисленные битсеты. В хранилище один базовый сегмент и до трёх дельта-сегментов. См. [История в журнале, текущее состояние в сегментах](engine.html#log-and-segments).

Синхронизация (sync) {#term-sync}
: `moirai sync`: слияние `main` в текущую линию типизированным слиянием, чтобы линия получила правила, завершения и удаления, записанные на `main`. Коммит синхронизации хранит только остаток — ключи, слитое значение которых отличается от того, что дали бы одни изменения `main`. См. [Как держать линию в актуальном состоянии: sync](versions.html#sync).

Слот `HEAD` (HEAD slot) {#term-head-slot}
: Один из двух слотов по 4 КиБ с контрольными суммами в файле `HEAD` хранилища; слоты называют текущие файлы сегментов, докуда читатели могут читать журнал, и несколько счётчиков. Публикация пишет более старый слот, а читатель берёт действительный слот с большим порядковым номером, поэтому разорванная запись одного слота вреда не причиняет. См. [Устойчивость к сбоям](engine.html#crash-safety).

Сначала красный (red-first) {#term-red-first}
: Правило собственного процесса разработки проекта: каждое утверждение о поведении и каждый новый или изменённый гейт сначала показывают падающими по предсказанной причине на коде без изменения, а затем проходящими с ним. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Совместное вливание (combined landing) {#term-combined-landing}
: В собственном процессе разработки проекта — набор юнитов, которые нужно влить вместе, потому что тест одного читает текст или байты другого, например тестовые фикстуры и оракул, который их декодирует. Набор тестируется как одно целое и вливается разом или не вливается вовсе. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Состояние ссылки (link state) {#term-link-state}
: Состояние одного якоря файловой ссылки в данном рабочем дереве, например `ok`, `moved-auto`, `moved-needs-confirm`, `missing`, `replaced` или `stale-anchor`. Оно вычисляется во время чтения, а строки состояний заморожены, чтобы скрипты могли на них полагаться. См. [Состояния ссылок](file-links.html#link-states).

Статус `proposed` (proposed status) {#term-proposed-status}
: См. [`proposed`](#term-proposed).

Страничный кэш (page cache) {#term-page-cache}
: Кэш содержимого файлов в памяти операционной системы. Поскольку сегменты Klotho отображаются только для чтения, все процессы Moirai на одной машине делят там одну копию горячих данных. См. [Много процессов, ни одного сервера](engine.html#process-model).

Строка учёта (ledger line) {#term-ledger-line}
: Строка `incr` в файле `.moi`: одна запись журнала счётчика, со знаковым изменением и id коммита. Значение счётчика — сумма его строк, поэтому приращения, сделанные на двух ветках, сохраняются оба. См. [Счётчики как строки учёта](git-image.html#counters).

Структурное нарушение (structural violation) {#term-structural-violation}
: Результат слияния, который сломал бы сам граф, например ребро блокера к узлу, удалённому другой стороной (`DanglingEdge`), или цикл блокеров. Он никогда не попадает на ветку: слияние останавливается на [промежуточный ref](#term-staging-ref). См. [Структурные нарушения останавливают слияние](versions.html#violations).

Структурное ребро (structural edge) {#term-structural-edge}
: Ребро, которое несёт правило, соблюдаемое движком, например порядок работы (`parent`, `blocks`, `gates`) или ответ на вопрос. Оба его конца должны быть живыми узлами — кроме [помеченного](#term-flagged-edge) ребра блокера. См. [Рёбра](concepts.html#edges).

Схема как данные (schema as data) {#term-schema-as-data}
: Схема Moirai — виды, поля, виды рёбер и именованные запросы — сама хранится в графе: версионируется по веткам, сливается и экспортируется, как всё остальное. Добавления проекта действуют сразу; изменение пункта или вывод его из употребления требует явной миграции. См. [Схема как данные](concepts.html#schema).

Сцепленный трейлер (chained trailer) {#term-chained-trailer}
: Короткое значение контрольной суммы в конце каждой группы записей в [журнале](#term-log), сцепленное со значением предыдущей группы. Прежде чем сообщить об успехе, писатель читает свой сцепленный трейлер обратно, поэтому группа, потерянная из-за неудачного сброса другого процесса, обнаруживается и записывается повторно, а не объявляется закоммиченной. См. [Один сброс на многих писателей](engine.html#group-commit).

Тег (tag) {#term-tag}
: Постоянное имя одного коммита в `tags/`, которое никогда не сдвигается. `moirai tag NAME --pin` вдобавок сохраняет там снимок, чтобы позже эту точку можно было быстро читать. См. [История](versions.html#history).

Типизированное слияние (typed merge) {#term-typed-merge}
: Слияние Moirai, которое знает тип каждого ключа: статусы объединяются по порядку вида, приращения счётчиков складываются, множества объединяются, текст сливается построчно, а настоящее расхождение становится [конфликтным значением](#term-conflict-value). См. [Типизированное трёхстороннее слияние](versions.html#merge).

Тихий режим (quiet mode) {#term-quiet-mode}
: `moirai quiet on` — для окон бенчмарков на той же машине. Он отключает обслуживание, которое писатели иначе выполняли бы на переднем плане, например автоматические чекпоинты (до потолка), rollup, сборку мусора и экспорт образа. Линия в статусе `measuring` подразумевает тихий режим. См. [Тихий режим](engine.html#quiet-mode).

Точка закрепления (settle point) {#term-settle-point}
: Момент, когда выполняется [закрепление](#term-settle): хук начала сессии, `moirai links sync`, явные файловые команды и `links fix`, `complete`, ритуал слияния и необязательный git-хук `post-commit`. См. [Закрепление](file-links.html#settling).

Трейлер (trailer) {#term-trailer}
: Строка вида `Key: value` в конце сообщения коммита git. Каждый коммит git в образе несёт трейлеры `Klotho-*`, которые содержат все поля канонической формы коммита Moirai, поэтому id коммита можно пересчитать после полного круга через git. См. [Коммиты и трейлеры](git-image.html#commits).

Трёхстороннее слияние (three-way merge) {#term-three-way-merge}
: Слияние, которое сравнивает обе стороны с их [базой слияния](#term-merge-base). Слияние Moirai типизировано: оно сравнивает ключи — например одно поле одного узла, одно ребро или существование одного узла, — а не строки файлов, и решает каждый ключ по правилу для его типа. См. [Типизированное трёхстороннее слияние](versions.html#merge).

Узел (node) {#term-node}
: Одна запись в графе, например задача, правило, решение или файл проекта. У каждого узла есть [вид](#term-kind), короткий id `#N`, постоянный [uid](#term-uid) и название, а также, по желанию, однострочная аннотация и тело до 64 КиБ. См. [Узлы и их id](concepts.html#nodes-and-ids).

Уровень (tier) {#term-tier}
: В собственном процессе разработки проекта — глубина, на которой выполняется юнит: LIGHT для текстовых изменений без изменения поведения, HEAVY для поведения продукта, устойчивости к сбоям, байтов и id, изменений правил и открытых решений, и STANDARD для всего остального. В сомнительных случаях применяется более высокий уровень. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Ускоритель (accelerator) {#term-accelerator}
: То, что экономит вызов или держит агента в более актуальном состоянии, но от чего ничего не зависит. Каждый [хук](#term-hook) Moirai — ускоритель с запасным путём: без него агент теряет немного свежести или делает на один вызов больше, но никогда не теряет корректность. См. [Хуки](agents.html#hooks).

Условие compare-and-set (compare-and-set guard) {#term-compare-and-set-guard}
: Полное название [CAS-условия](#term-cas-guard).

Фаза порта (port phase) {#term-port-phase}
: Запланированный этап после релиза для Windows, на котором строятся реализации для Linux и macOS. Он описан со своими гейтами, но не включён в график; порт может добавить реализацию, но никогда не меняет формат. См. [Linux и macOS — позже](building.html#ports).

Фаззинг (fuzzing) {#term-fuzzing}
: Тестирование парсера большим числом сгенерированных, часто некорректных входов. Каждый парсер в Moirai получает фаззер: записи журнала и сегменты, файлы `.moi`, объекты git, текст запросов и аргументы командной строки. См. [Направление тестирования](building.html#test-workstream).

Файл `.moi` (.moi file) {#term-moi-file}
: Файл узла в [git-образе](#term-git-image): канонический текст, который начинается с `klotho-node 1`, за которым идут строки заголовка, поля, метки, строки учёта и рёбра, а после строки `---` — тело. Каждый файл назван по [uid](#term-uid) узла. См. [Файл узла](git-image.html#node-file).

Файл `LOCK` (LOCK file) {#term-lock-file}
: Файл хранилища с диагностикой и записями сессий; байты, которые блокируют процессы, — для [блокировки писателя](#term-writer-lock) и [байта сброса](#term-flush-byte) — лежат за его концом. Он никогда не отображается в память. См. [Файлы хранилища](engine.html#store-files).

Файл-указатель (pointer file) {#term-pointer-file}
: Небольшой файл `.moirai`, который пишет `moirai init --link STORE` и который называет существующее хранилище, чтобы его находили команды, запущенные в другом каталоге. См. [Где лежит хранилище](engine.html#store-location).

Файловая ссылка (file link) {#term-file-link}
: Указатель от узла на файл проекта или место внутри него: [ребро `at`](#term-at-edge) к [файловому узлу](#term-file-node) с одним или несколькими якорями. Она следует за файлом через переименования, перемещения и правки, а если не может уверенно проследить за ним, показывает [состояние ссылки](#term-link-state) и следующий шаг. См. [Файловые ссылки, устойчивые к перемещениям](file-links.html).

Файловый узел (file node) {#term-file-node}
: Узел вида `artifact`, который представляет один логический файл проекта. Его идентичность фиксируется при первой регистрации файла; перемещение меняет его текущий путь, а прежние пути сохраняются как [алиасы](#term-alias). См. [Файловые узлы сохраняют идентичность](file-links.html#file-identity).

Форк (fork) {#term-fork}
: Создание ветки от коммита. Форк ничего не копирует: он записывает точку ответвления и сохраняет снимок, с которого начинается ветка; проектная оценка — около 2 мс. См. [Создать ветку дёшево](versions.html#cheap-forks).

Формат объектов (object format) {#term-object-format}
: Хэш-функция, которой репозиторий git вычисляет id объектов: SHA-1 или SHA-256. Образы по умолчанию используют SHA-1 для всего, что покидает машину, SHA-256 допускается для локальных репозиториев, и одно место назначения никогда их не смешивает. См. [Когда происходит экспорт](git-image.html#cadence).

Харнесс (harness) {#term-harness}
: Программа, которая запускает AI-агента для программирования, например Claude Code или Codex. Moirai нужно от харнесса немногое: команда `moirai` в `PATH`, MCP-сервер через stdio, короткий блок в `AGENTS.md` и переносимый skill. См. [Харнессы](agents.html#harnesses).

Хвост журнала (tail) {#term-tail}
: Самая новая часть [журнала](#term-log), ещё не свёрнутая в сегмент. Каждый процесс проигрывает её в свой [оверлей](#term-overlay); её длину ограничивает порог чекпоинта, поэтому открытие хранилища остаётся дешёвым. См. [История в журнале, текущее состояние в сегментах](engine.html#log-and-segments).

Хранилище (store) {#term-store}
: Каталог, в котором лежат все данные Moirai для проекта: журнал, сегменты и ещё несколько файлов. Внутри репозитория git это `<git-common-dir>/moirai/`, общий для всех рабочих деревьев; вне репозитория — `.moirai/`. См. [Где лежит хранилище](engine.html#store-location).

Хук (hook) {#term-hook}
: Код, который харнесс запускает по событию, например при старте сессии или отправке промпта. Хуки Moirai кладут в контекст агента бриф, ролевой пак или короткий список изменений и записывают доказательства для файловых ссылок. Они необязательны и [не мешают работе при сбое](#term-fail-open): любой их эффект можно получить и обычным вызовом. См. [Хуки: необязательные ускорители](agents.html#hooks).

Чекпоинт (checkpoint) {#term-checkpoint}
: Два связанных значения. В движке чекпоинт сворачивает самую новую часть журнала, [хвост](#term-tail), в новый дельта-[сегмент](#term-segment), чтобы открытие хранилища оставалось дешёвым. В git-образе коммит-чекпоинт — это один коммит git, который хранит состояние ветки на момент экспорта и сворачивает промежуточные коммиты; это гранулярность экспорта по умолчанию. См. [Чекпоинты, rollup и сборка мусора](engine.html#maintenance) и [Коммиты и трейлеры](git-image.html#commits).

Чужой коммит (foreign commit) {#term-foreign-commit}
: Коммит git в образе, который записал не Moirai или трейлеры которого не проходят проверку, например ручная правка файла `.moi`. При импорте его изменения становятся обычными типизированными изменениями с детерминированным id коммита и проверяются теми же валидаторами, что и слияние. См. [Правки, сделанные через git](git-image.html#foreign).

Эпоха (epoch) {#term-epoch}
: Случайное число, которое выбирается при создании хранилища и записывается в заголовок каждой записи журнала, поэтому запись действительна только в своём хранилище. Восстановление из резервной копии даёт хранилищу новую эпоху. См. [История в журнале, текущее состояние в сегментах](engine.html#log-and-segments).

Эталонная модель (reference model) {#term-reference-model}
: Полная, намеренно наивная реализация логики Moirai на Rust, написанная до движка и используемая только в тестах, в роли оракула. Там, где движок оптимизирует, модель использует прямое определение, и начиная с M1 движок сравнивается с ней команда за командой, включая id коммитов. См. [Эталонная модель](building.html#reference-model).

Эхо чтения (reading echo) {#term-reading-echo}
: Строка в начале результата Lachesis, которая словами говорит, что означает паттерн ребра, например `reads: b BLOCKS #211 ... | b must finish before #211 starts`. Она появляется, когда паттерн начинается с фиксированного узла на ребре, оба конца которого могут быть одного вида, или когда в нём используется [обратный алиас](#term-reverse-alias). См. [Паттерны: виды, рёбра и направления](lachesis.html#patterns).

Юнит (unit) {#term-unit}
: В собственном процессе разработки проекта — одна пригодная для ревью часть работы одной [авторской роли](#term-author-role): не больше примерно десяти коммитов и пятнадцати файлов, выполняется на ветке роли в её собственном рабочем дереве. См. [Строят AI-агенты по строгому процессу](building.html#agent-process).

Якорь (anchor) {#term-anchor}
: Часть [файловой ссылки](#term-file-link), которая говорит, где именно в файле: весь файл или одно место внутри него, например диапазон строк, элемент Rust или раздел Markdown. Якорь хранится как цитата с контекстом, окно хэшей строк и охватывающая область видимости, но никогда не как голый номер строки. См. [Что хранит якорь](file-links.html#what-an-anchor-records).
