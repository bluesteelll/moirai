# Файловые ссылки, устойчивые к перемещениям

Задача, заметка или правило в Moirai могут ссылаться на файл проекта или на фрагмент внутри него. Ссылка следует за файлом, когда его переименовывают, перемещают или правят. Если уверенно проследить за файлом нельзя, ссылка прямо говорит об этом и называет следующий шаг. Она никогда не укажет молча не на тот файл или не на тот текст.

## Проблема: цитаты устаревают {#the-problem}

Агенты ссылаются на код так же, как люди: `src/conn.rs:120`, `docs/design/routing.md`, «функция `read_request`». В день написания такая цитата верна. Потом проект меняется.

- **Строки сдвигаются.** Одна правка выше строки 120 — и номер указывает уже на другой код, а читатель об этом не узнаёт.
- **Файлы перемещаются.** Люди переименовывают файлы в редакторе. Агенты запускают `mv`, `Move-Item` или переименование на Python. Git переписывает дерево при `checkout`, `merge`, `rebase`, `stash`, `apply` и других командах. Большинство перемещений проходит мимо `git mv`, поэтому инструмент, который обновляет ссылки только при собственных перемещениях, их пропускает.
- **Файлы исчезают.** Файл удаляют. Иногда позже по тому же пути появляется новый файл, никак не связанный со старым.

Для агента цитата, которая молча указывает не на тот код, хуже битой: агент читает не тот текст и верит ему. Поэтому у каждой ссылки, которая не вполне верна, есть видимое состояние и однострочный следующий шаг.

Moirai сочетает два механизма. Явные файловые команды точно записывают перемещение или удаление. Во всех остальных случаях Moirai находит файл заново по доказательствам при следующем чтении ссылки, а новое место записывает, только если доказательство точное.

## Что такое ссылка {#what-a-link-is}

Ссылка — это ребро `at` от любого узла к [файловому узлу](glossary.html#term-file-node). Ребро несёт один или несколько [якорей](glossary.html#term-anchor). Якорь указывает на весь файл или на одно место внутри него, поэтому одна задача может ссылаться на несколько мест в одном файле. Агенты пишут якоря в тех формах, которыми уже пользуются:

| Форма | На что указывает якорь | Пример |
|---|---|---|
| `path` | на весь файл | `docs/design/routing.md` |
| `path:L-M` | на диапазон строк; хранится его текст, а не номера | `src/http/parse.rs:40-44` |
| `path::Type/fn` | на элемент Rust или ключ TOML | `src/conn.rs::Conn/read_request` |
| `path#Heading` | на раздел Markdown | `docs/design/routing.md#Fallback` |
| `path@<commit>:L-M` | на закреплённую историческую цитату, которая никогда не разрешается заново | `docs/design/routing.md@c4f1a9e20:12-18` |
| цитата (`--quote-file FILE`) | на буквальный текст; он должен встречаться в файле один раз или быть сделан уникальным | — |

```console
$ moirai link 204 --at src/parse.rs:40-44

```

*Спроектированный вывод.*

Пути задаются относительно корня проекта. Голое имя файла, под которое подходят несколько файлов, отвергается уже при записи ссылки, и в ответ выводится список совпадений. Так неоднозначная цитата никогда не попадает в хранилище.

> [!NOTE]
> **Статус двух форм**
>
> Формы `path::Type/fn` и `path#Heading` зависят от небольших сканеров для Rust, Markdown и TOML, которые находят элементы и заголовки. Спецификация сканеров написана, но ещё проходит ревью. Пока ревью её не примет, Moirai отвергает эти две формы и предлагает вместо них форму `path:L-M` для тех же строк. Если сканеры не успеют к заморозке формата на диске, отказ сохранится до следующего изменения формата.

### Что хранит якорь {#what-an-anchor-records}

Якорь никогда не бывает голым номером строки. При записи ссылки Moirai один раз читает файл и сохраняет набор селекторов — в типичном случае около 345 байт:

- **Цитата с контекстом:** точный текст и текст до и после него; контекст расширяется, пока цитата не станет уникальной в файле. При необходимости добавляется охватывающая область видимости (когда сканеры будут приняты), а в крайнем случае — номер вхождения. Для длинных фрагментов сохраняется ещё и цитата их конца.
- **Окно контекста:** хэши до 16 строк с каждой стороны; по ним различаются одинаковые цитаты.
- **Область видимости (scope):** охватывающий элемент Rust, путь заголовков Markdown или ключ TOML. Пока спецификация сканеров на ревью (см. врезку выше), ни один якорь область видимости не записывает.
- **Подсказка строки**, id содержимого файла и коммит git на момент захвата, а также хэш фрагмента.
- **Режим наблюдения:** `header` сохраняет ссылку на функцию или раздел актуальной, пока их тело растёт; `span` сообщает о любом изменении процитированного текста.

### Файловые узлы сохраняют идентичность {#file-identity}

Файловый узел — это узел вида `artifact`. Его идентичность вычисляется один раз: из корня, из пути, по которому файл зарегистрировали впервые, и из узла, который занимал этот путь до него. Перемещение меняет текущий `path` узла, но не его идентичность. Прежние пути хранятся как `aliases`: они разрешают старые упоминания, но никогда не захватывают новый файл. Две ветки, которые ссылаются на один и тот же файл, создают один и тот же узел.

Узел хранит и id содержимого `oid` — хэш байтов файла в формате git-блоба. Идентификатор файла в операционной системе (file id) служит лишь подсказкой в пределах одного рабочего дерева: редакторы при сохранении заменяют файл, и он получает новый id.

## Чтение никогда не пишет {#reads-are-pure}

Каждое чтение вычисляет состояния ссылок на лету, по файлам вашего рабочего дерева: `show`, `pack`, `brief`, `get`, `find`, `q`, `links check` и чтения MCP. Ни одно из них ничего не дописывает в журнал. Поэтому перемещённый или исчезнувший файл виден каждому ссылающемуся узлу при следующем чтении, без какой-либо записи.

Если чтение находит перемещённый файл, оно показывает `moved-auto` с деталью `not yet recorded`; в версионированную историю новое место попадает позже, в [точке закрепления](#settling) (settle point). Чтения по-прежнему обходятся без блокировок. Файл, который агент отодвинул в сторону для теста и потом вернул, будет записан, только если закрепление выполнится, пока файла нет на месте, и его повторная проверка тоже не найдёт файл. Перемещение на временный, игнорируемый или внешний путь не записывается никогда.

## Состояния ссылок {#link-states}

У каждого якоря ссылки в данном рабочем дереве ровно одно состояние. Строки состояний заморожены, поэтому агенты и скрипты могут на них полагаться.

| Состояние | Смысл |
|---|---|
| `ok` | Файл на своём пути, а процитированный текст там же, где был, или найден без изменений. |
| `moved-auto` | Файл найден по новому пути по точному доказательству. |
| `moved-needs-confirm` | Кандидат один, но доказательство неточное: похожий файл, идентичная копия или файл, который переместили и отредактировали. |
| `ambiguous` | Кандидатов два или больше, либо есть коллизия или конфликт, которые разрешит только решение. |
| `deleted` | Файл удалили намеренно, с причиной и, возможно, с заменой, или удалён его узел. |
| `replaced` | Путь существует, но файл по нему пересоздан с посторонним содержимым. |
| `stale-anchor` | Файл найден, но процитированный текст отредактирован, стал неоднозначным или исчез. |
| `missing` | Файла нет, и кандидатов тоже нет. |
| `absent-in-tree` | Это рабочее дерево не может содержать наблюдение: оно отстаёт или его история разошлась. |
| `pending` | Файл переместили на линии истории, которую это дерево ещё не получило. |
| `planned` | Ссылка создана с `--planned` на файл, которого ещё нет. |
| `unverified` | Сейчас состояние определить нельзя. Деталь называет одну причину из закрытого списка, например `budget`, `cloud-only`, `no tree`, `git` или `size`. |

Когда одно состояние должно обобщать несколько якорей, как в общем состоянии узла или в заголовке контекст-пака, побеждает самое серьёзное в таком порядке: `missing`, `replaced`, `deleted`, `ambiguous`, `moved-needs-confirm`, `stale-anchor`, `unverified`, `pending`, `planned`, `absent-in-tree`, `moved-auto`, `ok`. `replaced` стоит выше `deleted` намеренно: удаление — это записанное намерение, которое уже видит каждый ссылающийся узел, а по заменённому пути лежит постороннее содержимое, которое читатель может принять за процитированный файл.

<details>
<summary>Как сочетаются состояния файла и якоря</summary>

Состояние ссылки — это состояние файла, уточнённое состоянием якоря. Состояние якоря вычисляется, только если файл разрешился в `ok` или `moved-auto`. Якорь бывает `fresh` (текст там, где говорит подсказка), `moved` (тот же уникальный текст в другом месте файла), `edited` (близкое совпадение, или уцелела только область видимости), `ambiguous`, `orphaned` (ничего не найдено) или `unverified`. `edited`, `ambiguous` и `orphaned` переводят ссылку в `stale-anchor`; якорь `unverified` делает её `unverified`.

Файл, удалённый намеренно, или удалённый файловый узел делает каждый ссылающийся узел `suspect`: это состояние графа, и оно записывается в том же коммите. Все остальные состояния вычисляются во время чтения по рабочему дереву и никогда не мешают задаче быть готовой к работе. В запросах значения `none` (узел без ссылок) и `unresolved` (якорь, файл которого не разрешился) нужны для того, чтобы встроенные функции давали ответ для любого входа; см. [Lachesis](lachesis.html).

</details>

## Сеанс проверки ссылок {#links-check-session}

Пусть у небольшого HTTP-сервера `tinyhttp` есть задача-кампания `#200` «Поддержка HTTP/2» с подзадачами, которые ссылаются на файлы. С тех пор как цитаты были написаны, агент переместил парсер; кто-то переименовал проектную заметку и переписал её часть в редакторе, который сохраняет файл заменой; фазз-тест удалили; заметку о бенчмарках переписали с нуля; а строки с процитированной функцией переписали. `moirai links check` выводит каждую ссылку под `#200`, которая не в состоянии `ok`; `--deep` добавляет поиск по сходству для файлов, которых не нашло ни одно точное доказательство:

```console
$ moirai links check --scope 200 --deep
branch: main | rev 4512 | live | 5 rows | files @ tinyhttp (main 3f9c2a1, dirty 2 5m ago)
#812  moved-auto            src/parse.rs -> src/http/parse.rs  file-id | not yet recorded (moirai links sync)
#815  moved-needs-confirm   docs/design/router.md -> docs/design/routing.md  similar 0.81, runner-up 0.22 | verify #815
#820  missing               tests/fuzz_headers.rs  since 3m | no candidate | nothing written
#826  replaced              docs/bench.md  re-created with unrelated content (containment 0.04/0.07) | verify #826
a31  stale-anchor          src/conn.rs:118-131  edited 0.86 | was: "pub fn read_request(b..." | verify a31
verify #N: moirai file where N --evidence

```

*Спроектированный вывод.*

В заголовке указаны ветка, ревизия, `live` (результат зависит от рабочего дерева) и само дерево: его метка, ветка git, `HEAD` git и число изменённых файлов. Каждая строка начинается с дескриптора: `#N` для файлового узла, `aN` для отдельного якоря.

`#812 moved-auto`
: Парсер переместился; это доказывает его file id при неизменных размере и времени изменения. Перемещение запишет `moirai links sync` или следующее автоматическое закрепление.

`#815 moved-needs-confirm`
: Переименованная и отредактированная заметка на 81 % похожа на прежнее содержимое. Сходство — это догадка, поэтому Moirai только предлагает; `moirai file where 815 --evidence` показывает доказательства.

`#820 missing`
: Тестового файла нет, и ничего похожего тоже нет. Ничего не записано. Если удаление было намеренным, его запишет `moirai links fix 820 --drop`.

`#826 replaced`
: По старому пути есть файл, но с процитированной версией у него почти ничего общего. Ответ — `--accept-replacement` или `--drop`.

`a31 stale-anchor`
: Файл на месте, но процитированные строки изменились; сходство ближайшего совпадения — 0,86. `was:` показывает начало процитированного текста.

Ни одна строка не печатает команду, которая принимает догадку: предложения указывают на команду просмотра доказательств, точные состояния — на команду закрепления. Прочитав доказательства, агент выполняет `moirai links fix 815 --accept --expect docs/design/routing.md`; команда срабатывает, только если лучшее предложение всё ещё указывает на этот путь. После этого ссылка показывается как принятая догадка, пока её не подтвердит через `--confirm` другой актор, роль которого это позволяет (по умолчанию `orchestrator` или `owner`).

Контекст-паки и брифы показывают для каждой ссылки не в состоянии `ok` одну короткую метку, например `[moved-needs-confirm 0.81 | verify #815]`, не длиннее 50 байт, плюс одну строку-легенду для команды `verify`.

Когда чтение обнаруживает, что путь ссылки исчез, Moirai действует в три шага.

1. **Спросить собственную историю git этого дерева.** Moirai прямо в процессе, не запуская git, читает дерево последнего коммита git в этом рабочем дереве. Если путь ссылки там всё ещё есть, значит, это дерево само переместило или удалило файл и ещё не закоммитило изменение, поэтому запускается поиск. Поиск запускается и тогда, когда дерево уже получило коммит, из которого взято последнее наблюдение. Если же там есть один из прежних путей файла, перемещение произошло на линии истории, которую это дерево ещё не получило: `pending`, без поиска. Иначе Moirai ищет точные переименования в коммитах, которые это дерево интегрировало; если ни одно из них не объясняет изменение, состояние — `absent-in-tree`.
2. **Искать по доказательствам**, начиная с самых сильных. Кандидатами бывают только пути, которые не занимает другой живой файловый узел, и никогда — пути вне корня, в игнорируемом выводе сборки, с временными или резервными именами, облачные заглушки (cloud-only) и файлы в корзине.
3. **Классифицировать.** Один точный кандидат даёт `moved-auto`, два и больше — `ambiguous`, более слабый кандидат — `moved-needs-confirm`, отсутствие кандидатов — `missing`. Исчерпанный бюджет даёт `unverified` и никогда не даёт догадку.

<details>
<summary>Доказательства в том порядке, в каком их проверяют</summary>

- **Записанное намерение:** запись намерения `file mv` или цепочка file id, которую необязательный хук записал сразу после `mv` агента.
- **Id родительского каталога.** NTFS сохраняет id каталога при переименованиях и перемещениях, поэтому один поиск перепривязывает все связанные файлы под перемещённым каталогом; у macOS и Linux есть свои аналоги. Найденный там файл всё равно должен совпасть.
- **Собственный id файла**, проверенный размером и временем изменения или содержимым, потому что файловые системы переиспользуют id.
- **Соседние каталоги, старые пути и записанные перемещения каталогов.**
- **Точные переименования внутри одного коммита git**, прочитанные из деревьев git. Идентичные блобы никогда не спариваются по порядку.
- **Поиск по id содержимого** среди файлов, созданных после последнего закрепления.
- **Перемещён и отредактирован:** новый файл с тем же именем, содержимое которого совпадает со старым не меньше чем на 80 % в обе стороны. Это только предложение.

Равное содержимое — ещё не идентичность: кандидат с тем же id содержимого считается точным, только если это подтверждает переименование git внутри одного коммита или записанное намерение (на Windows также равное время создания, уникальное в просмотренной области). Файл, который существовал рядом с оригиналом, — это копия и никогда не цель. Поиск по сходству работает только под `--deep` и только предлагает. Существующий путь, у которого изменились и содержимое, и file id, а пересечение меньше 29 % в обе стороны, получает `replaced`. Все пороги — константы версии резолвера, поэтому одно и то же дерево всегда даёт один и тот же ответ.

</details>

<details>
<summary>Как якорь снова находит свой текст</summary>

Moirai пробует подсказку строки, затем точную цитату внутри области видимости якоря, затем во всём файле; между дублями выбирает по контексту и окну. Дальше идёт нечёткое сравнение: оно требует сходства не ниже 0,75 и явного отрыва от следующего кандидата. Переименованная функция сопоставляется только с заголовком того же вида, поэтому `acquire` никогда молча не станет `acquire_shared`. Если уцелела только область видимости, якорь получает `edited`; если не найдено ничего — `orphaned`. Совпадение, ближайшее к старому номеру строки, Moirai не выбирает никогда.

</details>

## Закрепление: когда записывается новое место {#settling}

Чтения показывают, где файл находится сейчас; закрепление (settle) записывает это место в версионированную историю. Точки закрепления: хук `SessionStart` (для брифа сессии и собственных файлов линии, с жёстким потолком 150 мс), `moirai links sync`, явные файловые глаголы и `links fix`, `complete` (отдельным коммитом после коммита самой задачи), ритуал слияния и необязательный блок git-хука `post-commit`. Правила того, что может записать закрепление, строгие:

- **По умолчанию автоматически перепривязывает только точное доказательство:** идентичность файла, записанное намерение или переименование git внутри одного коммита, причём при единственном кандидате. При ничьей перепривязки нет. Ключ конфигурации может разрешить перепривязку и по единственному сильному предложению; такая перепривязка остаётся помеченной как догадка, пока её кто-нибудь не подтвердит.
- **Одно лишь равное содержимое никогда не перепривязывает.** Идентичный файл может оказаться резервной копией, зеркалом или вендорной копией.
- **Отсутствие никогда не означает удаления.** Пропавший файл сохраняет ребро и последний путь, которые видит каждый ссылающийся узел, пока кто-нибудь не примет решение. Удаление записывают только `file rm`, `links fix --drop`, `--same-as` или `--split`, а также закрепление, которое по точному переименованию git объединяет два файловых узла, претендующих на один путь. Исключение — если ключ конфигурации велит Moirai принимать коммиты с удалениями, замеченные в главном дереве.
- **Повторно использованный путь показывается как `replaced`**, а не молча как `ok`.
- **Пишет только дерево-писатель ветки.** У каждой ветки не больше одного назначенного рабочего дерева: для линии — рабочее дерево, которое называет `moirai lane open`; для `main` — дерево из ключа конфигурации `files.main-tree`; для любой другой ветки — единственное дерево, привязанное командой `moirai worktree bind DIR BRANCH`, которая отвергает второе дерево для той же ветки. У ветки без назначенного дерева нет дерева-писателя, и все деревья для неё только читают. Назначенное дерево записывает перепривязки, только пока его `HEAD` в git находится на той линии истории git, которая соответствует ветке, и только для файлов, последнее наблюдение которых оно уже получило. На `main` оно записывает только перемещения, закоммиченные в его `HEAD`. Все остальные деревья — читатели: их наблюдения ждут в виде отложенных строк, пока дерево-писатель не увидит то же перемещение.
- **Сначала проверка тишины.** Закрепление повторно проверяет каждый старый путь не раньше чем через 50 мс после того, как в последний раз видело его отсутствующим, и отменяет перепривязку, если путь вернулся: редакторы, которые сохраняют файлы атомарно, на несколько миллисекунд переименовывают оригинал.
- **Без потерянных обновлений.** Каждая перепривязка защищена ревизией файлового узла, прочитанной в начале разрешения; если узел за это время изменился, перепривязка ждёт следующего закрепления.

## Явные глаголы {#explicit-verbs}

Глаголы, которые работают с самими файлами, собраны под `moirai file` и `moirai links`, потому что `add`, `rm`, `move` и `link` уже заняты глаголами узлов. Сама файловая ссылка создаётся глаголом узлов `moirai link` с опцией `--at` и удаляется через `moirai unlink --at`.

| Команда | Что делает |
|---|---|
| `moirai link ID --at SPEC` | Захватывает якорь и записывает ссылку одним коммитом; `--planned` ссылается на файл, которого ещё нет. |
| `moirai unlink ID --at aN\|PATH` | Удаляет один якорь, а вместе с последним якорем и ребро. |
| `moirai file add PATH..` | Регистрирует файлы, не создавая ссылок. |
| `moirai file mv SRC.. DST` | Перемещает файлы или каталог с устойчивой к сбоям записью намерения и одним коммитом перенаправляет все ссылки. |
| `moirai file rm PATH..` | Удаляет намеренно, с `--reason` и `--replaced-by`; без `--yes` это пробный прогон. |
| `moirai file relink PATH --to PATH --after` | Записывает перемещение, уже сделанное другими средствами. |
| `moirai file revert COMMIT` | Возвращает файлы на место для коммита, который их переместил или удалил. |
| `moirai file where PATH\|ID --evidence` | Показывает текущий путь в каждом дереве, старые пути, предложения и доказательства. |
| `moirai links check` | Перечисляет ссылки не в состоянии `ok`; никогда не пишет. |
| `moirai links sync` | Закрепление: записывает все точные перепривязки, которые допускают правила. |
| `moirai links fix ID\|aN ...` | Записывает решение: принять, подтвердить, указать путь, отбросить, заново захватить якорь. |
| `moirai links mentions` | Сообщает об упоминаниях старых путей в обычном тексте; файлы никогда не переписывает. |
| `moirai links import --from-markdown GLOB` | Разовая миграция существующих цитат `path:line` из Markdown в ссылки; перечисляет те, которые не удалось точно разместить. `--dry-run` показывает план. |

`file mv`, `file rm` и `file revert` меняют файловую систему, поэтому доступны только из командной строки и работают только в дереве-писателе вашей ветки. В других местах они отказываются с кодом выхода 5 и предлагают обычный `mv`; ссылки последуют за файлами по доказательствам, когда код дойдёт до дерева-писателя. Перемещение между томами отвергается с кодом выхода 7: у копирования с последующим удалением нет порядка, который пережил бы отключение питания. Индекс git Moirai трогает только с `--git`.

<details>
<summary>Устойчивый к сбоям протокол команд file mv и file rm</summary>

1. **План**, только чтение: проверить дерево, место назначения и каждый затронутый файловый узел, старый путь и glob путей.
2. **Намерение:** дописать в журнал долговечную запись намерения.
3. **Файловая система:** переименовать, ничего не заменяя, затем сбросить на диск оба родительских каталога, чтобы переименование стало долговечным раньше коммита, который его записывает. Каталог перемещается одним переименованием.
4. **Коммит:** один коммит перенаправляет все затронутые узлы, сохраняет старые пути как алиасы, записывает перемещение каталога, переписывает glob путей под ним и закрывает намерение.
5. **Восстановление:** после сбоя следующий писатель или `moirai doctor` решает по состоянию файловой системы: докатить, если переименование произошло; отменить, если нет; пометить `ambiguous`, ничего не удаляя, если по обоим путям лежат разные файлы.

`file rm` работает так же. Его коммит записывает `removed` с причиной и заменой, перенаправляет на замену ссылки на весь файл и те якоря, текст которых в ней найден, и делает каждый ссылающийся узел `suspect`.

</details>

## Рабочие деревья, ветки и git-образ {#worktrees-and-branches}

Агенты часто работают одновременно в нескольких рабочих деревьях git одного репозитория, а у Moirai есть собственные ветки (см. главу [«Ветки, слияния и история»](versions.html)). Поэтому файловые ссылки живут в двух слоях:

|  | Намерение ссылки | Разрешение |
|---|---|---|
| Содержимое | файловые узлы, якоря, рёбра `at`, намерение удаления, история перемещений каталогов | состояния ссылок, file id ОС, кэши, доказательства, предложения |
| Область | одна ветка | одно рабочее дерево |
| Версионируется и сливается | да | нет |
| Попадает в git-образ | да | никогда |

Git версионирует файлы, Moirai версионирует ссылки. Ветки несут намерение ссылок, слияния объединяют его по типизированным правилам, а [git-образ](git-image.html) его экспортирует: файловые узлы становятся обычными файлами `.moi`, якоря — строками `anchor` в файле ссылающегося узла, и ничего машинно-локального никогда не экспортируется. Место назначения можно настроить так, чтобы оно получало якоря без текста цитат.

Разрешение выполняется отдельно в каждом рабочем дереве. Дерево, которое ещё не получило перемещение, сообщает об этом через `pending` или `absent-in-tree`, а не перепривязывает ссылку обратно. Слияния никогда не читают файловую систему и поэтому остаются чистыми функциями истории; расхождение в пути становится конфликтным значением, которое позже разрешает закрепление по наблюдению. Команды истории, такие как `undo` и `revert`, никогда не трогают рабочее дерево: ссылки следуют за файлами, где бы те ни лежали.

## Ни наблюдателя, ни процесса git, ни работы в простое {#no-watcher}

Moirai не запускает ни наблюдателя за файлами (watcher), ни демона, ни таймера, ни цикла опроса. Вся работа происходит внутри команд и хуков, которые вы запускаете, поэтому в простое CPU не расходуется. Кроме того, наблюдатель терял бы события, а на Windows его дескрипторы подкаталогов мешают переименовывать их родительские каталоги.

Доказательства из git поставляет встроенный в процесс читатель объектов git. Ни одно разрешение ссылки не запускает процесс git; единственный такой процесс в этой части Moirai — включаемый явно `file mv --git`. Без git всё по-прежнему работает, только без доказательств из git, и пропавший файл никогда не считается удалённым.

Хуки — необязательные ускорители, каждый включается своим ключом конфигурации. Хук `PostToolUse` на `mv`, `rm` или `Move-Item` агента записывает цепочку file id, пока она ещё точна. Там, где харнесс выполняет хуки как вызовы инструментов MCP, не запуская нового процесса, хук правки после каждой правки обновляет id связанного файла; благодаря этому правка с последующим перемещением остаётся точной. Блоки git-хуков устанавливаются только по запросу, командой `moirai hooks install --git`.

Moirai открывает файлы проекта только для чтения с полным совместным доступом, по одному за раз, и никогда не отображает их в память, не блокирует, не пишет в них и не добавляет к ним id или альтернативные потоки данных. Облачные заглушки (cloud-only) никогда не скачиваются автоматически; такие ссылки показывают `unverified (cloud-only)`.

## Бюджеты времени {#time-budgets}

Разрешение ссылок стоит на пути каждого чтения, поэтому у него свои бюджеты. Это проектные цели, а не замеры:

| Ситуация | Цель |
|---|---|
| Работа со ссылками для контекст-пака с 50 ссылками, все файлы на месте | ≤ 3 мс по медиане в простое, ≤ 5 мс под нагрузкой |
| Тот же пак, все 50 файлов в одном перемещённом каталоге | ≤ 5 мс по медиане |
| Тот же пак, 10 файлов отредактированы после последнего закрепления | ≤ 5 мс по медиане |
| Работа с git на пути чтения | ≤ 10 мс на 99-м процентиле |
| Закрепление в `SessionStart` | ≤ 150 мс и ≤ 16 КБ журнала, если ничего не изменилось |
| Байты журнала, записанные чтениями; CPU в простое | ноль; ноль |
| Память для чтения, которое разрешает якоря в файле размером 16 МиБ | ≤ 4 МБ |

Чтения измеряют работу с файловой системой в единицах, а не во времени, поэтому при одном и том же состоянии дерева чтение всегда останавливается на одной и той же ссылке. Ссылки, до которых чтение не дошло, получают `unverified (budget)`, а команда завершается с кодом 10. Язык запросов показывает те же состояния через `link_state()`; см. [Lachesis](lachesis.html).
