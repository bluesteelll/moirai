Под капотом: Klotho

Moirai — это одна программа, moirai. Внутри неё работает Klotho — движок хранения, написанный с нуля ради одной задачи: держать небольшой версионируемый граф на локальном диске, открывать его примерно за миллисекунду и давать многим процессам агентов одновременно читать его и писать в него без сервера. В этой главе рассказано, где лежат данные, как запись становится долговечной, что происходит после сбоя и в какие бюджеты движок должен укладываться по проекту.

Спроектировано, но ещё не построено

Эта глава описывает проект. Движок будет построен в вехе M1 — после заморозки версии 1 формата на диске (см. Как это строится и где проект сейчас). Все числа ниже — целевые значения проекта, а не измеренные результаты готового продукта.

Один бинарник с движком внутри

По замыслу Moirai — один статический бинарник на Rust. Интерфейс командной строки, хуки, которые вызывает харнесс, и MCP-сервер — это один и тот же исполняемый файл moirai, запущенный с разными аргументами. Klotho — библиотека, скомпилированная в этот бинарник. Это не отдельный сервис, и больше ничего устанавливать или запускать не нужно.

Klotho — не обёртка над готовой базой данных: в проекте нигде не используются ни SQLite, ни какой-либо сторонний движок хранения. Журнал, сегменты, протокол блокировок, система контроля версий и слой git-объектов пишутся вручную на Rust. Когда появятся крейты движка, они получат имена klotho-*; продукт, бинарник и команда останутся moirai.

Где лежит хранилище

Хранилище — это каталог. moirai init создаёт его там, где агенты найдут его без дополнительной настройки:

в любом каталоге, с --link STOREновое хранилище не создаётся; появляется небольшой файл-указатель .moirai, который ссылается на существующее

Каждая команда ищет своё хранилище в одном и том же порядке: явный --store DIR, переменная окружения MOIRAI_DIR, подъём по дереву каталогов в поисках .moirai и, наконец, подсказка от объемлющего git-репозитория. Поиск никогда не создаёт хранилище; если ничего не найдено, команда перечисляет все пути, которые проверила.

Хранилище работает только на локальной файловой системе, которую покрывают краш-тесты; на Windows это NTFS. Сетевые диски, папки с облачной синхронизацией вроде OneDrive, FAT, exFAT, ReFS и пути внутрь WSL отвергаются с указанием причины. С хранилищем работает только одно ядро операционной системы, потому что блокировки диапазонов байтов не действуют через границу ядра.

Файлы хранилища

Обычно в хранилище около дюжины файлов: HEAD, LOCK, config, до четырёх экстентов журнала, один базовый и до трёх дельта-сегментов и, возможно, словарь сжатия. Другие файлы добавляются, когда старая история уходит в архив, тела запечатываются, а ветки продвигаются (promotion). Все файлы, кроме HEAD, LOCK, config, экстентов журнала и каталогов tmp/ и trash/, запечатаны: каждый записывается один раз, делается долговечным, помечается на диске как доступный только для чтения и больше никогда не меняется.

Для всех файлов действуют несколько общих правил. Хранилище растёт за счёт новых файлов. Файлы никогда не усекаются, а файл, который какой-то процесс может держать отображённым, никогда не заменяется переименованием поверх него. Файл удаляется только после того, как HEAD уже 60 секунд (льготный период) указывает на другие файлы, а ни одна ветка или тег его больше не закрепляет. Файлов на отдельный узел или коммит нет, поэтому число файлов не растёт вместе с размером графа.

Почему в память отображаются только запечатанные файлы

Отображение в память позволяет каждому процессу читать одни и те же байты прямо из страничного кэша операционной системы, без копирования. Но на Windows размер отображённого файла нельзя изменить, а отображённое представление не согласуется с обычными записями в тот же файл. Поэтому Klotho отображает только файлы, которые больше никогда не меняются, а журнал читает и пишет явными вызовами ввода-вывода. Каждый запечатанный файл указывает свою длину в заголовке, и перед отображением она сверяется с настоящим размером файла.

История в журнале, текущее состояние в сегментах

Klotho хранит два представления одних и тех же данных.

  • Журнал — каноническая история. Каждое изменение дописывается в него записью с 32-байтовым заголовком: длина записи, её позиция в журнале (log sequence number, LSN), эпоха хранилища (случайное число, выбранное при его создании) и контрольная сумма xxh3. Запись валидна только на своей позиции и только в своём хранилище. Ничто в журнале не переписывается на месте.
  • Сегменты хранят текущее состояние главной ветки по колонкам: заголовки узлов, названия и поля, исходящие и входящие рёбра каждого узла в компактных массивах, заранее вычисленные битсеты, которые отвечают на вопросы вроде «какие задачи разблокированы», таблицу символов и ссылки на тела. Сегменты неизменяемы. Их строят из журнала чекпоинты.

Между двумя чекпоинтами самая новая часть журнала, хвост, ещё не входит ни в один сегмент. Каждый процесс воспроизводит хвост в небольшой оверлей в памяти. Чтобы найти узел, читатель смотрит сначала в оверлей, затем в дельта-сегменты от новых к старым и, наконец, в базовый сегмент.

Такое разделение делает открытие хранилища дешёвым. При открытии читается HEAD, отображается не больше восьми файлов сегментов и воспроизводится хвост, длину которого ограничивает порог чекпоинта. Ни один шаг не читает всю историю, поэтому стоимость открытия не растёт с её длиной. Цель проекта для открытия хранилища с тёплым кэшем и полным хвостом — не больше 1 мс при 10 000 узлов и не больше 3 мс при 1 000 000 узлов.

Насколько мал коммит

Коммит хранит чистый набор изменений: выполненные операции, каждую со значением до изменения (before-image), так что любой коммит можно обратить для undo и revert. Типичный небольшой коммит агента с одним родителем, коротким сообщением и несколькими операциями оценивается в 0,35–0,5 КБ до сжатия. Подходы, при которых каждый коммит копирует целые страницы дерева, платят килобайтами за каждое мелкое изменение; набор изменений обходится байтами.

Большинство запросов читает около 99 байт на узел; эти байты лежат в страничном кэше, общем для всех процессов moirai.

Адресация по содержимому

У каждого коммита есть id — хеш BLAKE3-256 от канонической формы коммита. Каноническая форма — это заданная спецификацией последовательность байтов: вид коммита, его родители, значение часов, кто его сделал, git-коммит, относительно которого он сделан, сообщение, версия схемы, коммит, который он отменяет (revert) или переносит (cherry-pick), и git-коммит, из которого он импортирован (каждое из этих полей пусто, если значения нет), а также дайджест его чистого набора изменений. Два хранилища с одним и тем же коммитом вычисляют одинаковый id, а git-образ содержит все поля, нужные, чтобы пересчитать id после перехода в git и обратно. Данные, которые принадлежат только одному хранилищу, например собственный id хранилища, в хешируемую форму не входят.

Длинные текстовые тела тоже адресуются по содержимому, 128-битным хешем BLAKE3, поэтому одинаковое тело хранится один раз. Главы Ветки, слияния и история и Сохранение в git показывают, как используются эти id.

Много процессов, ни одного сервера

Нет ни демона, ни серверного процесса, который держал бы граф в памяти. Каждая команда moirai, которую запускает агент, порождает процесс: он открывает хранилище, делает свою работу и завершается. MCP-сервер, который запускает сессия харнесса, — тот же бинарник в долгоживущем режиме. Для движка это просто ещё один клиент: он отображает те же файлы и берёт те же блокировки.

ПроцессВремя жизниЧто он делает с хранилищем
команда или хук moiraiмиллисекундычитает напрямую; блокировку писателя берёт только на шаг коммита
moirai mcpодна сессия агентадержит свои отображения и небольшой кэш представлений веток с ограничением по размеру; между запросами выполняет плановое обслуживание порциями не длиннее 5 мс

Читатели не берут блокировок. Они читают неизменяемые сегменты через отображения в память, поэтому страничный кэш операционной системы держит одну копию горячих данных для всех процессов на машине. Журнал они воспроизводят только до границы, опубликованной в HEAD, поэтому читатель никогда не увидит долговечное изменение раньше, чем завершится покрывающий его сброс на диск.

Писатели работают по очереди. Блокировку писателя в каждый момент держит не больше одного процесса: это исключительная блокировка одного байта файла LOCK. На Windows это LockFileEx, на Linux и macOS — блокировка open file description (OFD). Писатель ждёт блокировку ограниченное время, которое задаёт ключ конфигурации (в проекте — 2 секунды; значение по умолчанию закрепит замер в M0). Если время ожидания вышло, команда не зависает, а завершается с сообщением, в котором назван процесс, держащий блокировку.

В фоне ничего не опрашивается. Нет ни таймеров, ни наблюдателей за файлами, ни циклов опроса. Единственное обслуживание, которое переживает команду, — дочерний процесс rollup, описанный ниже: процесс запускает его отсоединённым, когда пересечён порог, а тот выполняет свою единственную работу и завершается. У MCP-сервера не больше двух потоков операционной системы, и в простое оба заблокированы. Потребление CPU в простое равно нулю по построению.

Почему не демон

Демон, который держит граф в RAM, занимал бы память размером с весь набор данных даже тогда, когда ни один агент не работает, а это нарушает бюджет памяти; к тому же демоны не раз становились источником отказов в прежних инструментах для агентов. Необязательный процесс-«лидер», который пересылает записи, описан в спецификации, но его построят, только если замеры покажут, что он нужен; корректность от него никогда не зависит.

Запись в три фазы

Каждая команда записи, от изменения одного поля до слияния ветки, проходит три фазы, чтобы блокировка писателя удерживалась как можно короче.

  1. Расчёт, без блокировки. Процесс открывает хранилище, догоняет журнал, определяет свою ветку, проверяет изменение (схему, охранные условия, аренду, правила статусов, отсутствие циклов) и по снимку строит полный набор изменений и его каноническую форму.
  2. Коммит, под блокировкой. Процесс берёт блокировку писателя и просматривает всё, что другие писатели дописали после его снимка. Если ничто из этого не затронуло то, что изменение читает или записывает, подготовленный коммит за постоянное время присоединяется к новой вершине ветки; иначе он один раз пересчитывается или фаза 1 выполняется заново, но не больше двух раз. Процесс дописывает свои записи одной группой и отпускает блокировку. При простой записи блокировка удерживается десятки микросекунд. Затем процесс делает группу долговечной через групповой коммит (следующий раздел), для чего снова берёт блокировку писателя, но лишь ненадолго.
  3. После коммита. Процесс печатает результат и, если превышен какой-то порог, выполняет часть обслуживания.

Один сброс на многих писателей

Запрос к диску на сброс данных (flush) — самый медленный шаг коммита. Если бы каждый писатель сбрасывал данные сам, шестнадцать агентов, закончивших одновременно, ждали бы шестнадцать сбросов подряд.

Вместо этого Klotho использует групповой коммит без лидера. Писатель, чья группа ещё не долговечна, берёт второй байт блокировки — байт сброса, — а затем снова блокировку писателя. Он заново записывает несброшенный диапазон журнала, отпускает блокировку писателя и выполняет один сброс. Затем он на мгновение снова берёт блокировку писателя, чтобы опубликовать новый слот HEAD, который покрывает все группы, дописанные до начала сброса. Писатель, который дописал свою группу за это время, видит, что она уже покрыта, и сам сброс уже не выполняет. Цели такие: не больше одного сброса на долговечный коммит, ровно один для писателя, который работает в одиночку, и не больше трёх сбросов на всплеск из шестнадцати писателей.

Ни один процесс не играет роль координатора, поэтому протокол работает и для агентов в песочницах, которые не могут связаться с другим процессом. Контрольная сумма каждой группы сцеплена с контрольной суммой предыдущей группы. Прежде чем сообщить об успехе, писатель перечитывает собственный сцепленный трейлер. Если из-за неудачного сброса в другом процессе операционная система отбросила несброшенные страницы, потерянная группа обнаружится именно здесь, и писатель повторит запись с тем же ключом идемпотентности, а не сообщит о коммите, которого нет на диске.

Устойчивость к сбоям

Движок спроектирован так, чтобы процесс можно было убить на любой инструкции, а машина могла упасть в любой момент, и при этом ни один подтверждённый коммит не потерялся.

  • Всё или ничего. Записи пишутся группами, например коммит вместе с записями аренды и маркера. Восстановление принимает группу целиком или не принимает вовсе, и журнал заканчивается на первой неполной или невалидной группе. Поэтому задача никогда не окажется завершённой без маркера, который не даёт другим веткам снова выдать её в работу.
  • Подтверждено — значит долговечно. О выполнении коммита сообщается только после того, как завершился сброс, начатый уже после записи коммита, изменения коммита опубликованы, а писатель проверил собственный сцепленный трейлер.
  • Истина — журнал; HEAD — кэш. У HEAD два слота по 4 КиБ с контрольными суммами. Публикация записывает новое состояние в более старый слот, а читатель берёт валидный слот с бо́льшим порядковым номером, поэтому частичная (разорванная) запись одного слота вреда не наносит. HEAD не сбрасывается на диск при каждом коммите; в нём записано, до какого места журнал заведомо долговечен, и загрузка системы, во время которой хранилище было создано или в последний раз восстановлено после перезагрузки. После перезагрузки первый процесс заново просматривает журнал от последней долговечной точки и один раз сбрасывает HEAD, прежде чем кто-либо начнёт читать, поэтому ни один читатель не увидит картину, какой она была до сбоя.
  • Неудачный сброс фатален. Процесс останавливается. Следующий процесс, который выполняет сброс, заново записывает несброшенный диапазон и не доверяет страницам, которые могли быть отброшены.
  • Удаление ждёт обоих слотов. Прежде чем обслуживание удалит или переиспользует любой файл, оба слота HEAD приводятся к новому состоянию и HEAD сбрасывается на диск, поэтому ни один уцелевший слот не может указывать на удалённый файл.

moirai doctor --verify заново вычисляет каждую производную структуру и вершину каждой ветки и сравнивает их с сохранёнными; moirai doctor --fsck проверяет контрольные суммы; moirai repair --rebuild-from-log перестраивает из журнала все сегменты и файлы истории.

Признанный пробел

Эти гарантии проверяются на симулированной файловой системе, которая внедряет сбои, полным перебором точек краша и циклами, которые убивают настоящие процессы на Windows (см. направление тестирования). Стенд, который раз за разом роняет виртуальную машину с Windows или жёстко отключает ей питание, перенесён на время после релиза. Пока он не заработал, устойчивость к реальной потере питания остаётся явно названным и непроверенным риском, а проект исходит из того, что диск честно выполняет запрос на сброс.

Классы долговечности и тихий режим

Не всем записям нужна одинаковая защита. У каждого вида записи есть класс долговечности, и каждый класс на каждой операционной системе соответствует конкретным системным вызовам.

Долговечный сброс — это NtFlushBuffersFileEx с флагом «только данные» на Windows, fdatasync на Linux и fcntl(F_FULLFSYNC) на macOS и никогда не более слабый вызов. Если место хранения не может обеспечить класс, хранилище там отвергается, а не работает молча с ослабленными гарантиями.

Тихий режим

moirai quiet on нужен на время бенчмарков на той же машине. Он отключает обслуживание, которое иначе выполняли бы занятые писатели на переднем плане: автоматический чекпоинт не запускается, пока хвост журнала не дорастёт до кратного обычного порога (по проекту — восьмикратного; окончательное значение задаст замер в M0), и тогда выполняется ровно один ограниченный чекпоинт; rollup, продвижение веток, сборка мусора, экспорт и импорт образа не выполняются, если их не запустить принудительно. Линия в статусе measuring включает этот режим сама; moirai quiet off выключает его.

Чекпоинты, rollup и сборка мусора

  • Дельта-чекпоинт. Когда хвост журнала перерастает порог (он считается в операциях, в байтах и в памяти оверлея), хвост сворачивается в новый дельта-сегмент, а его тела сжимаются и запечатываются в файл blobs. Это происходит вне блокировки писателя, и до следующей публикации читатели пользуются старыми сегментами. MCP-сервер делает эту работу порциями не длиннее 5 мс между запросами; процесс команды берётся за неё, только когда хвост превышает порог вдвое. Три дельта-сегмента сливаются в один.
  • Rollup. Когда дельта-сегменты превышают 25 % размера базового сегмента, пишется новый базовый сегмент. Rollup никогда не выполняется внутри MCP-сервера или процесса команды либо хука. Он работает только в отдельном процессе moirai gc, который запускают явно или порождают отсоединённым, с низким приоритетом по CPU, памяти и вводу-выводу. Входные данные он обрабатывает потоком, поэтому его память ограничена; цель — не больше 24 МБ при 100 000 узлов.
  • Вывод истории в архив. Заполненный экстент журнала сжимается в файл hist. По умолчанию ничего не удаляется.
  • Сборка мусора. moirai gc сохраняет всё, что достижимо из ветки, тега, пина (pin) или записи reflog моложе 90 дней (gc.reflog-expire). Недостижимые коммиты старше 14 дней (gc.cruft-delay) удаляются из истории; их заголовки остаются, если вы не попросите иначе. Файлы удаляются только после 60-секундного льготного периода (gc.delete-grace) и барьера двух слотов HEAD. Все три значения — ключи конфигурации.

Резервное копирование и восстановление

moirai backup DIR пишет копию хранилища, согласованную на границе коммита. Прежде чем сообщить об успехе, команда сбрасывает на диск каждый скопированный файл и каталог и записывает факт резервного копирования в журнал, поэтому предупреждение о возрасте последней резервной копии правдиво.

moirai restore DIR --into EMPTY_DIR ставит резервную копию на место под блокировками писателя и обслуживания, даёт восстановленному хранилищу новую эпоху и помечает старое хранилище как выведенное из работы, чтобы каждый долгоживущий процесс заново нашёл хранилище.

Вторая, независимая копия получается из git-образа. Политика экспорта по умолчанию записывает чекпоинт main при каждом слиянии в main и раз в день — для main и для каждой живой линии, так что даже у неслитой работы на линии есть копия вне хранилища. См. Сохранение в git.

Сначала Windows, но Linux и macOS заложены в проект

Сначала всё собирается и тестируется на Windows: каждая веха до релиза реализуется и проходит гейты на Windows. Linux и macOS учитываются в проекте уже сейчас, а не потом. Формат на диске, протокол блокировок и коммита и слой операционной системы описаны в спецификации для всех трёх систем и замораживаются вместе с версией 1 формата. Реализации для Linux и macOS появятся в фазе портирования после релиза для Windows; эта фаза пока не запланирована. Порт может добавить реализацию, но никогда не может изменить формат или протокол.

  • Один формат. Все раскладки байтов — little-endian и 64-битные и не зависят ни от размера страницы, ни от разделителя путей. Резервная копия восстанавливается на другой системе, а образ импортируется где угодно.
  • Один протокол, рассчитанный на самую слабую систему. Правила исходят из самого тяжёлого поведения при сбоях среди трёх систем: записи каталога, которым нужна собственная синхронизация; неудачные сбросы, которые могут отбросить страницы; позднее освобождение блокировок после краша; повторно используемые номера inode. Тестовый симулятор файловой системы воспроизводит эту модель, поэтому тесты на Windows уже проверяют поведение Unix при сбоях.
  • Один слой ОС. Код, зависящий от операционной системы, есть только в одном крейте, который сейчас называется moirai-os. Линт отвергает cfg(windows), std::os и прямое использование windows-sys или libc в любом другом месте. Для каждой целевой платформы у каждого интерфейса ровно одна реализация, которая выбирается при компиляции.
  • Только чистый Rust. Ни одна зависимость не может компилировать или линковать C, C++ или ассемблер. При каждом слиянии рабочее пространство проходит проверку типов для Linux на x86-64 и ARM64 и для macOS на ARM64 с отключёнными тулчейнами C, поэтому зависимость, которой нужен нативный код, сразу даёт ошибку. Из этой проверки исключены только тонкая точка входа бинарника, которую проверяют для Windows, и несколько прошедших ревью тестовых инструментов, которые работают только на хост-машине.

Как проверяются бюджеты. У каждого бюджета указаны его гейт и веха, с которой гейт обязателен; после этого он остаётся обязательным. Гейты времени и памяти выполняются по письменному протоколу замеров на эталонной машине с Windows 11 и включённой антивирусной проверкой в реальном времени — и в простое, и при воспроизведении записанной нагрузки из 16 агентов; размер выборки зависит от длительности измеряемой операции. Часть гейтов задана относительно физической нижней границы, измеренной в том же прогоне, например стоимости одного сброса, поэтому они не зависят от конкретного диска. Облачные раннеры CI собирают код, выполняют линты и прогоняют модульные, property- и дифференциальные наборы тестов на синтетических данных; это лишь сигнал корректности и никогда не гейт по времени. Бюджеты токенов проверяет реестр токенов (token ledger): он записывает все байты, которые moirai помещает в контекст агента, и пересчитывает их в токены токенизатором той модели, которую запускает харнесс.

Конфигурация

Каждая эксплуатационная политика — это ключ конфигурации с типом и документированным значением по умолчанию. Поведение меняется установкой ключа, а не пересборкой.

  • Две области действия. Ключи хранилища лежат в <store>/config и действуют для каждого процесса и рабочего дерева, которые пользуются хранилищем, поэтому все писатели ведут себя одинаково. Пользовательские ключи, например пути на этой машине и способ поиска хранилищ, лежат в %APPDATA%\moirai\config на Windows и в $XDG_CONFIG_HOME/moirai/config на Linux и macOS. У каждого ключа ровно одна область действия.
  • Приоритет. Флаг командной строки важнее переменной окружения, переменная окружения важнее файла конфигурации, а файл важнее встроенного значения по умолчанию.
  • Типизированный реестр. Бинарник знает тип, диапазон, значение по умолчанию, область действия и класс перечитывания каждого ключа, и moirai config list --defaults всё это печатает. moirai config set проверяет значение и отклоняет недопустимое. В файле, отредактированном вручную, неизвестный ключ даёт предупреждение, а вместо недопустимого значения берётся значение по умолчанию; moirai config check и moirai doctor сообщают и о том, и о другом.
  • Перечитывание. Процессы команд и хуков читают конфигурацию при каждой команде. Долгоживущий MCP-сервер замечает изменение по счётчику в HEAD, который увеличивает config set, и перечитывает конфигурацию при следующем запросе.

Файлы записываются в синтаксисе git-config:

# moirai store configuration
default-branch = main
[gc]
    reflog-expire = 90d
    cruft-delay = 14d

moirai config get KEY печатает действующее значение ключа.
