# Сохранение в git

Moirai умеет записывать весь свой граф и его историю в обычный git-репозиторий: по небольшому текстовому файлу на узел и по одному git-коммиту на каждый коммит Moirai или на каждый чекпоинт. Любой git-инструмент может читать такой репозиторий, показывать по нему диффы и переносить его, а Moirai может загрузить его обратно, вместе с правками, которые люди сделали через git. Источником истины остаётся хранилище. Git — это место для хранения и переноса копии данных, а для работы Moirai git никогда не нужен.

## Зачем записывать граф в git {#why}

Эта копия называется [git-образом](glossary.html#term-git-image). Она даёт четыре вещи:

- **Перенос.** Образ — обычный git-репозиторий, поэтому его можно перенести через любой удалённый репозиторий (remote), а простой `git clone` забирает все экспортированные ветки и теги.
- **Ревью.** Каждый узел — это текстовый файл. `git diff` точно показывает, какие задачи, правила и заметки изменились, и любой инструмент код-ревью может показать изменение человеку.
- **Загрузка обратно.** Образ импортируется в другое хранилище или в то же самое после того, как люди отредактировали его через git. Каждый импортированный коммит проверяет тот же движок слияния, который работает при локальном слиянии.
- **Копия вне хранилища.** По умолчанию хранилище лежит внутри git-каталога проекта и пропало бы вместе с ним. Ежедневный экспорт `main` и каждой живой линии сохраняет копию всей работы, включая ещё не влитую, в отдельном репозитории.

Устройство образа определяют два правила. Первое: отображение — чистая функция от данных. Два хранилища, у которых есть один и тот же коммит Moirai и которые отбросили одни и те же тела, пишут для него побайтно одинаковые git-объекты в назначения с одинаковым форматом объектов и одинаковой настройкой записи цитат якорей. Второе: хранилище канонично. Образ производен от него, и git никогда не просят ответить на запрос.

## Как выглядит образ {#tree}

Каждый git-коммит образа содержит дерево с фиксированной раскладкой:

```text
.klotho-image                    the format marker
nodes/<h1>/<h2>/<uid>.moi        one file per node, live or deleted
schema/kinds.moi                 the project's own kinds
schema/fields.moi                the project's own fields and values
schema/edges.moi                 the project's own edge kinds
schema/policy.moi                policy rows
schema/queries/<q>.moi           one file per saved named query
refs/heads.moi, refs/tags.moi    checkpoint commits only: the checkpointed ref
```

- **Файлы называются по uid.** У каждого узла есть [uid](glossary.html#term-uid) — 128-битная идентичность, записанная 32 шестнадцатеричными цифрами; у большинства видов она случайная. `<h1>` — первые две её цифры, а `<h2>` — следующие две, так что файлы распределяются по 65&nbsp;536 небольшим каталогам. Коммит, который затрагивает k узлов, переписывает только корневое дерево, дерево `nodes/` и не больше k деревьев на каждом из двух уровней под ним; всё остальное в git остаётся общим с предыдущим коммитом.
- **Никаких коротких id.** Короткие id, которые вы набираете, например `#31`, принадлежат одному хранилищу, поэтому их нет ни в именах файлов, ни в содержимом файлов. Собственные номера хранилища передаются отдельно, как подсказка (см. [Куда попадает образ](#destination)).
- **Переносимые имена.** Каждое имя в дереве — это шестнадцатеричная строка в нижнем регистре или фиксированное ASCII-слово, поэтому дерево извлекается на файловых системах, не различающих регистр, в Windows, Linux и macOS.
- **Только исходящие рёбра.** Ребро записывается в файл того узла, из которого оно выходит. Добавление «#31 blocks #33» меняет только файл `#31`, а импортёр восстанавливает входящие рёбра. Правило, на которое ссылаются тысячи узлов, не меняется при каждой новой ссылке.
- **У удалённых узлов остаётся файл.** Удалённый узел становится файлом-надгробием, который хранится всё время жизни образа. Поэтому файл, исчезнувший из дерева, всегда означает удаление, сделанное вне Moirai.

Файл-маркер содержит ровно три строки: версию формата образа, формат git-объектов репозитория и версию схемы.

```text
klotho-image 1
object-format: sha1
schema-version: 1
```

В дереве нет ничего, что принадлежит одному хранилищу: ни id хранилища, ни коротких id, ни порядковых номеров. Именно поэтому два хранилища пишут для одного и того же коммита одно и то же корневое дерево.

## Файл узла {#node-file}

Файл узла — канонический текст: для данного состояния существует ровно одна правильная последовательность байтов, и в этой форме пишет только экспортёр. Вот задача из вымышленного проекта `tinyhttp`, файл `nodes/1d/60/1d603c9a852269c3c1999802c8096f81.moi`:

```moi
klotho-node 1
uid: 1d603c9a852269c3c1999802c8096f81
kind: task
title: Parse chunked request bodies
status: in_progress
priority: P1
parent: bb385cbb661b2c11aa530d9d4d0e1086
order: a1
created: caabe37fbc25f8f1060b7642d0afed1da6c1cdc823615a20f956f3b49fdd066f9 2026-10-29T11:02:47.508Z
updated: c6fc5a6ba2f9796994af5dddcfbed9d0d03f53ade37b98e02a819f2fff618473b 2026-11-03T16:40:12.031Z
field assignee: dev#2
field estimate: 3
field work_kind: impl
label http1
label parser
incr reopen_count +1 cf01a96e74df2272dd98c9e459ce44971b10f55714559e773b82fa94ab18404ea
edge blocks -> 76283b800bb759c8971d23cff0681316
edge cites -> 3c0d6718493b2f50b2382e744ed8d4b4 pin=cd29c8a17ca87c083b4956969e5b1d2a370fc3e850f174eb3982c3feeead985ba
edge mentions -> 50fd4f8ea2c235126ef09a2c10f6cd4e
---
Read each chunk size as hexadecimal and reject sizes above max_body.
Trailer fields after the last chunk are ignored for now.


```

Разберём его сверху вниз:

- `klotho-node 1` называет формат файла и его версию. (Klotho — движок хранения внутри Moirai; образ использует его имя.)
- Строки заголовка идут в фиксированном порядке: `uid`, `kind`, `title`, `status`, `resolution`, `priority`, `criticality`, `confidence`, `authority`, `parent`, `order`, `created`, `updated`, `deleted`, `flags`. Строка `priority`, `criticality`, `confidence` или `authority` со значением по умолчанию не пишется, как и строка `resolution` со значением `none`; строка `status:` пишется при любом статусе, включая начальный статус вида. Критичность этой задачи — значение по умолчанию, `normal`, поэтому строки `criticality:` нет, а у задачи с приоритетом по умолчанию `P2` не было бы строки `priority:`.
- `parent` и `order` задают место узла в дереве задач. Ссылка на другой узел — всегда uid этого узла.
- `created` и `updated` называют коммиты, которые создали узел и последними изменили этот файл, а за id каждого коммита идёт его время в виде, понятном человеку. Импортёр использует только id коммита из `created`.
- Строки `field` хранят остальные поля, отсортированные по имени; строки `label` хранят метки.
- Строка `incr` — одна запись учёта счётчика (см. [ниже](#counters)).
- Строки `edge` — исходящие рёбра узла. `pin=` привязывает цитирование к одному коммиту.
- Всё, что после `---`, — тело.

Производное состояние никогда не записывается: ни `ready`, ни число открытых блокеров, ни флаг «конфликтный». Импортёр всё это вычисляет заново.

### Тела сохраняются побайтно {#bodies}

Тело записывается байт в байт, и за ним следует ровно один дополнительный перевод строки, а при чтении ровно один перевод строки снимается. Поэтому тело, которое само заканчивается переводом строки, как в примере выше, даёт файл с двумя переводами строки в конце, а файл без перевода строки в конце не бывает никогда, так что `git diff` никогда не показывает «No newline at end of file». Жёсткие переносы Markdown (два пробела в конце строки), строка `---` внутри тела и несколько завершающих переводов строки — всё это сохраняется. Единственное изменение, которое вообще происходит с телом, делает хранилище при записи: CR LF и одиночный CR становятся LF. Импортёр применяет то же правило к файлу, который пришёл из git с CR LF, а в остальном байты не трогает.

Тело, которое хранилище отбросило, например секрет, вставленный по ошибке, экспортируется как хеш тела и причина, по которой его отбросили (`--- dropped <hash> secret`), но никогда как текст.

### Счётчики как строки учёта {#counters}

Счётчик вроде `reopen_count` никогда не бывает одной строкой `field`. Это журнал учёта (ledger): по строке `incr` на каждый коммит, который его изменил, с приращением со знаком и id коммита. Значение — сумма строк. Если счётчик увеличили обе ветки, они добавляют две разные строки, поэтому при объединении изменений ни одно увеличение не теряется.

### Конфликты в файле {#conflicts-in-files}

[Конфликтное значение](versions.html#conflicts), оставленное слиянием, тоже экспортируется — как строка `conflict` с классом и тремя сторонами. Пока такая строка есть, обычная строка для этого ключа не пишется. Для задачи с тремя открытыми конфликтами:

```moi
conflict body class=TextHunk base="Chunks are read into one buffer.\n" ours="Chunks are streamed to the handler.\n" theirs="Chunks are read into a pooled buffer.\n"
conflict field.estimate class=FieldEdit base=3 ours=5 theirs=
conflict status class=StatusFork base=in_progress ours=done/completed theirs=cancelled/obsolete
```

Пока конфликты не разрешены, в этом файле нет раздела тела после `---`, нет строки `field estimate:` и нет строки `status:`. Пустое `theirs=` означает, что эта сторона удалила оценку. Структурные нарушения в образе не появляются никогда: они существуют только на промежуточных refs, а промежуточные refs никогда не экспортируются.

<details>
<summary>Как выглядит файл удалённого узла</summary>

Надгробие хранит uid, вид, заголовок, удаляющий коммит, причину и замену, а также исходящие рёбра, которые хранилище сохраняет для мёртвого узла. Здесь задачу `#44` удалили без замены, когда она ещё блокировала `#31`:

```moi
klotho-node 1
uid: 6d34a01602266e14073edcf6b792dc62
kind: task
title: Fixed-length body limits
deleted: c919c2b236948a403dabebf30b6b6fa372b81d483c184ae329a57d9fbea8b2e8d 2026-11-04T10:21:09.442Z
field reason: superseded by the streaming reader
edge blocks -> 1d603c9a852269c3c1999802c8096f81 flagged
```

Помеченное (`flagged`) ребро блокера переживает экспорт и обратный импорт. После любого импорта `#31` остаётся вне очереди готовых задач, пока кто-нибудь не разрешит это ребро, поэтому удаление никогда не разблокирует работу незаметно.

</details>

## Коммиты и трейлеры {#commits}

Экспорт пишет git-коммиты с одной из двух гранулярностей, которая выбирается для каждого назначения отдельно:

- **`checkpoint`** (по умолчанию): один git-коммит на каждый экспорт каждой изменившейся ветки, с состоянием ветки на этот момент. Коммиты между экспортами сворачиваются в него.
- **`commit`**: один git-коммит на каждый коммит Moirai, с полной историей. Сюда входят все коммиты, достижимые из экспортированных веток через обоих родителей, поэтому коммиты `main`, на которые ссылается синхронизация линии, экспортируются вместе с линией.

Каждый git-коммит строится только из данных Moirai. Его дерево — образ в этом коммите. Его родители — git-коммиты, соответствующие его родителям в Moirai; у слияний и синхронизаций их два. Автор и коммитер — одна и та же строка, составленная из актора и роли коммита, например `klotho/dev#2 <developer@klotho.invalid>`, а время берётся из собственных часов коммита. Идентичность экспортёра и его системное время в коммит не попадают, подпись и дополнительные заголовки не пишутся, поэтому повторный экспорт того же коммита даёт те же байты.

Сообщение коммита — это сообщение Moirai, пустая строка и блок [трейлеров](glossary.html#term-trailer). Вот коммит, который последним изменил задачу выше, — захват задачи на `lane/chunked`:

```text
claim --start

Klotho-Commit: c6fc5a6ba2f9796994af5dddcfbed9d0d03f53ade37b98e02a819f2fff618473b
Klotho-Kind: ordinary
Klotho-Ref: lane/chunked
Klotho-Hlc: 117553496852463619
Klotho-Actor: dev#2
Klotho-Role: developer
Klotho-Session: claude:s7
Klotho-Git-Head: sha1:30be61019cea5cb18bae586f614ddff4c5a32a68
Klotho-Git-Branch: chunked
Klotho-Worktree: /work/tinyhttp-lanes/chunked
Klotho-Schema: 1
Klotho-Ops: 1
Klotho-Idem: 20a73b5a599d8486e079c2166fbd6f11
```

Id коммита Moirai — это хеш BLAKE3-256 канонической формы коммита. У каждого поля, которое входит в этот хеш, ровно одно место в git-коммите: вид коммита; id родителей — это трейлеры `Klotho-Commit` родительских коммитов; гибридные часы — в `Klotho-Hlc` (во времени автора миллисекунды теряются); актор, роль и сессия; контекст репозитория кода, в котором сделана запись (git head, ветка, рабочее дерево и база); сообщение; версия схемы; исходный коммит для revert или cherry-pick; и сами изменения, то есть разница между этим деревом и деревом первого родителя. Импортёр восстанавливает каноническую форму по этим носителям, заново вычисляет хеш и сравнивает его с `Klotho-Commit`. `Klotho-Ops` — дешёвая предварительная проверка: число изменений. `Klotho-Ref` и `Klotho-Idem` — справочные и не хешируются.

У checkpoint-коммита нет `Klotho-Commit`, потому что он представляет диапазон коммитов, а не один коммит. Его сообщение — `checkpoint <ref>` с трейлерами `Klotho-Kind: checkpoint`, `Klotho-Head` (самый новый коммит Moirai, который он покрывает), `Klotho-Ref` и `Klotho-Folded` (сколько коммитов он сворачивает, от какого и до какого). Его родитель — предыдущий чекпоинт той же ветки.

<details>
<summary>Все трейлеры</summary>

| Трейлер | Когда пишется | Хешируется? |
|---|---|---|
| `Klotho-Commit` | в каждом родном коммите | это и есть проверяемый id |
| `Klotho-Kind` | всегда: `ordinary`, `merge`, `sync`, `revert`, `cherry-pick` или `checkpoint` | да |
| `Klotho-Parent` | только когда заявленный id родителя отличается от того, что даёт его git-родитель | да |
| `Klotho-Head`, `Klotho-Folded` | в checkpoint-коммитах | нет |
| `Klotho-Ref` | ветка, на которую попал коммит | нет |
| `Klotho-Hlc` | в каждом родном коммите | да |
| `Klotho-Actor`, `Klotho-Role`, `Klotho-Session` | когда значение не пустое | да |
| `Klotho-Git-Head`, `Klotho-Git-Branch`, `Klotho-Worktree`, `Klotho-Git-Base` | когда запись сделана в рабочем дереве git | да |
| `Klotho-Origin` | в revert и cherry-pick | да |
| `Klotho-Sync-Base` | в синхронизациях: читаемая копия id второго родителя | нет (это копия) |
| `Klotho-Foreign-Git` | в коммите, который впервые импортирован из git и снова записан в другое назначение | да |
| `Klotho-Schema`, `Klotho-Ops` | в каждом родном коммите | `Klotho-Schema` — да; `Klotho-Ops` — нет |
| `Klotho-Idem` | в записях, которые несли ключ идемпотентности | нет |

Экспортёр пишет трейлеры в одном фиксированном порядке, а импортёр принимает их в любом. Трейлер с пустым значением не пишется.

</details>

## Куда попадает образ {#destination}

По умолчанию образ — это отдельный bare-репозиторий git рядом с проектом: `<parent of the main worktree>/<main worktree name>-moirai.git`. Для проекта, извлечённого в `/work/tinyhttp`, это `/work/tinyhttp-moirai.git`. Благодаря отдельному репозиторию история образа не раздувает репозиторий самого проекта. `moirai image export --create` настраивает его с явным форматом объектов, хранением refs в обычных файлах, отключённым автоматическим `git gc` и строкой `*.moi -text diff` в его `info/attributes`, чтобы git в этом репозитории не преобразовывал концы строк в файлах узлов. Клон этот файл не получает; если клон преобразует концы строк, импортёр превращает CR LF обратно в LF.

| Ref в Moirai | Git ref в репозитории образа |
|---|---|
| `main` | `refs/heads/main` |
| `lane/<name>` | `refs/heads/lane/<name>` |
| `plan/<name>` | `refs/heads/plan/<name>`, если выбран |
| `tags/<name>` | `refs/tags/<name>` |
| промежуточные refs (`merge/*`, `import/*`) | никогда не экспортируются |

По умолчанию экспорт выбирает `main`, `tags/*` и `lane/*`. Кроме них, каждое экспортирующее хранилище ведёт один побочный ref (side ref), `refs/klotho/meta/<store-id>`. Он никогда не входит в дерево какого-либо коммита и не хешируется. В нём лежат id хранилища, версия формата образа, гранулярность каждого экспортированного ref, последний экспортированный порядковый номер и файлы алиасов, которые сопоставляют каждому uid короткий id этого хранилища. Импортёр читает его только как подсказку. С `--with-oplog` второй побочный ref, `refs/klotho/ops/<store-id>`, переносит сдвиги указателей веток и клиентские HEAD, чтобы историю reflog можно было воспроизвести в другом месте.

### Когда происходит экспорт {#cadence}

- `main` получает чекпоинт после каждого слияния в `main` (настройка `image.export.on-merge-to-main`, по умолчанию включена), раз в день и при каждом явном экспорте.
- Каждая живая линия получает чекпоинт раз в день и при каждом явном экспорте. Его родитель — предыдущий чекпоинт линии, поэтому у невлитой работы линии всегда есть копия вне хранилища.
- Ежедневному экспорту не нужен таймер. Первый запуск сессии после того, как истёк срок `image.export.max-age` (по умолчанию один день), выполняет инкрементальный экспорт. Харнесс без хуков вместо этого запускает `moirai image export --if-older` — первым шагом оркестратора и на нескольких путях записи. Это делается по мере возможности: экспорт, который запретила песочница, печатает одну строку и никогда не приводит к сбою записи, которая его запустила, а `moirai brief` и `moirai doctor` предупреждают, когда последний экспорт слишком старый.

По умолчанию образы используют идентификаторы объектов SHA-1 — для всего, что покидает машину; SHA-256 допускается для локальных репозиториев. Одно назначение никогда не смешивает эти форматы, а `moirai doctor image` предупреждает, прежде чем образ SHA-256 будет отправлен в удалённый репозиторий, который не объявил его поддержку.

## Экспорт, импорт, push и pull {#export-import}

| Команда | Что делает |
|---|---|
| `moirai image export [--to DEST] [--refs ...] [--granularity checkpoint\|commit] [--create] [--if-older D]` | Записывает новые коммиты выбранных refs в репозиторий или bundle-файл. Экспорт инкрементальный: для каждого ref он идёт назад только до самого нового уже экспортированного коммита. |
| `moirai image import [--from DEST\|FILE] [--refs ...]` | Читает новые git-коммиты из репозитория или bundle-файла, проверяет их и дописывает в хранилище. |
| `moirai image push [REMOTE]` | Отправляет репозиторий образа в удалённый git-репозиторий. Если git установлен, запускает `git`, а иначе печатает точную команду. Отправляет только в удалённые репозитории, перечисленные в `image.allowed-remotes`. |
| `moirai image pull [REMOTE]` | Забирает изменения из удалённого репозитория, а затем импортирует их. |
| `moirai image doctor [--rebuild-map]`, `image show`, `image gc` | Сверяют образ с хранилищем, показывают один коммит образа и переупаковывают репозиторий образа. |

Хранилище ведёт таблицу [gitmap](glossary.html#term-gitmap): каким git-коммитом стал каждый коммит Moirai, для каждого назначения и формата объектов. Экспорт сначала пишет на диск свои pack-файлы и refs и лишь в последнюю очередь записывает их в gitmap. Поэтому после сбоя назначение может опережать gitmap не больше чем на один шаг — следующий экспорт это обнаружит и исправит, — но никогда не отстаёт от него. gitmap можно и перестроить по самому образу, прочитав трейлеры `Klotho-Commit`. Каждое обновление ref проверяет, что у ref всё ещё то значение, которое это хранилище видело последним; если его сдвинул кто-то другой, экспорт останавливается (код выхода 6) и просит сначала выполнить импорт.

Экспорт и импорт держат блокировку писателя хранилища только на время дописывания своих записей, поэтому, пока идёт экспорт, агенты продолжают работать. Проектная цель для инкрементального checkpoint-экспорта `main` и двух линий — не больше 50 мс.

Сессия в проекте `tinyhttp` в том виде, в каком она задумана. Сначала экспорт:

```console
$ moirai image export
export main tags/* lane/* (checkpoint, sha1) -> /work/tinyhttp-moirai.git
  main: 1 checkpoint commit (Klotho-Folded: 14 commits), 9 blobs, 21 trees
  lane/chunked: 1 checkpoint commit, 3 blobs; lane/keepalive: unchanged
  refs updated: refs/heads/main, refs/heads/lane/chunked, refs/klotho/meta/0c4e9a71...
```

*Спроектированный вывод.*

Затем коллега клонирует репозиторий образа обычным git. На `main` он исправляет опечатку в строке `title:` одного файла узла и делает коммит. На `lane/chunked` он выполняет `git merge --allow-unrelated-histories main` (при гранулярности checkpoint у цепочек чекпоинтов разных веток нет общих git-коммитов), получает текстовый конфликт в одном файле узла и коммитит этот файл, оставив в нём маркеры конфликта git. Обе ветки он отправляет обратно. Следующий импорт читает оба коммита:

```console
$ moirai image import
import refs/heads/main: 1 new git commit
  4be1a90 foreign  author git:dev@example.org "Fix typo in task title" -> 1 op SetField(#31.title) -> applied on main
import refs/heads/lane/chunked: 1 new git commit
  9c03d7e foreign merge  nodes/1d/60/1d603c9a852269c3c1999802c8096f81.moi: line 9 matches no rule (git conflict marker) -> staged on import/lane/chunked (ImageParse)
```

*Спроектированный вывод.*

У первого коммита нет трейлера `Klotho-Commit`, поэтому это [чужой коммит](glossary.html#term-foreign-commit) (foreign commit): изменённые в нём строки становятся одним обычным изменением поля на `main`. Второй коммит оставил маркеры конфликта git в файле узла. Этот файл не разбирается, поэтому коммит ждёт на промежуточном ref `import/lane/chunked`, а `lane/chunked` в хранилище не сдвигается.

### Правки, сделанные через git {#foreign}

Git-коммит, трейлеры которого проходят проверку, — это родной коммит: он дописывается со своим id и помечается как проверенный. Checkpoint-коммит (`Klotho-Kind: checkpoint`, без `Klotho-Commit`) импортируется как коммит импортированного чекпоинта с детерминированным id. Все остальные коммиты — чужие. Родной коммит, хеш которого не совпал, понижается до чужого только сам; его потомки по-прежнему проверяются по заявленным в них id родителей. Чужой коммит получает детерминированный id: его вид — `ordinary` (или `merge`, если родителей два), актор — `git:<author email>`, время берётся из времени коммитера и всегда позже, чем у родителей, сообщение — сообщение git, и вместе с ним записывается id git-коммита. Поэтому два хранилища, которые импортируют один и тот же чужой коммит, дают ему одинаковый id. Каждый импортированный коммит проверяют те же валидаторы, что и слияние.

| Что произошло в git | Что делает импорт |
|---|---|
| Файл `.moi` отредактировали вручную. | Чужой коммит. Изменённые строки становятся обычными изменениями: поля, статуса, ребра, тела. |
| Две экспортированные ветки слили через `git merge`. | Коммит импортируется как типизированное слияние Moirai, которое объединяет состояния двух родителей. Файлы, слитые git, нужны только для того, чтобы увидеть, как человек разрешил конфликтующие строки текста. Счётчики берутся из типизированного слияния и никогда — из текстового. Всё остальное, в чём стороны расходятся, становится конфликтным значением. |
| Файл узла удалили. | Чужое удаление; при следующем экспорте оно записывается обратно как надгробие. Если удалённый узел ещё блокировал другие задачи, его рёбра блокеров остаются, помеченные (flagged), и эти задачи остаются вне очереди готовых задач: ручное удаление никогда не разблокирует работу незаметно. |
| Историю переписали через rebase или squash. | Трейлеры сохраняются в сообщениях коммитов. Коммит, дерево которого совпадает с пересчитанным, снова сопоставляется со своим коммитом Moirai; остальные становятся чужими. Экспорт отказывается сдвигать ref, которого не узнаёт, пока не выполнен импорт. |
| Два хранилища экспортируют в один репозиторий. | Обновление ref у второго хранилища не проходит. Оно сначала импортирует, проверяя родные коммиты другого хранилища, а затем экспортирует. |

Если локальная ветка ушла вперёд с тех пор, как на ней были основаны импортированные коммиты, импортированная цепочка попадает на `import/<ref>`, и импортёр вливает её в локальную ветку типизированным слиянием относительно их последнего общего экспортированного коммита. Настройка `image.import-merge = stage` вместо этого откладывает каждый такой импорт, чтобы его слил человек.

Короткие id локальны для хранилища, поэтому импорт сопоставляет узлы по uid. Короткий id из побочного ref другого хранилища сохраняется, только если здесь он ещё свободен; иначе узел получает новый локальный номер, а `moirai show` печатает рядом старый, как в `#40 (was #17 in store 6f2a…)`. Текст импортированного тела никогда не перечитывается в поисках упоминаний `#N`, потому что эти номера принадлежат хранилищу, которое их записало; рёбра упоминаний берутся только из строк `edge mentions`.

### Когда файл не разбирается {#parse-errors}

Импорт никогда не принимает файл, которого не понимает. При следующих проблемах импорт откладывается на `import/<ref>` с нарушением `ImageParse` и путём к файлу; локальная ветка не сдвигается:

- оставшиеся маркеры слияния (строки `<<<<<<<`, `=======`, `>>>>>>>`);
- строка, которая не подходит ни под одно правило формата, или неизвестный ключ заголовка;
- повторённая строка, например две строки `status:` или две строки `conflict` для одного ключа;
- строка `uid:`, которая не совпадает с именем файла;
- вид узла, поле, вид ребра или значение, которых не знает схема коммита, или значение, которое не подходит к типу своего поля;
- отсутствующий или неверный маркер `.klotho-image` либо неожиданный файл в `nodes/`, `schema/` или `refs/`.

В рамках формата импортёр терпим. Он принимает метку порядка байтов (BOM), концы строк CR LF, пробелы в конце строк, строки в другом порядке, явно записанное значение по умолчанию и написанный вручную файл узла без строк `created:` и `updated:` — и всё это нормализует.

Отложенный импорт, нарушения которого называют ключ, завершается так же, как отложенное слияние: `moirai resolve` на `import/<ref>`, затем `moirai merge --continue import/<ref> --into <ref>` (см. [Структурные нарушения](versions.html#violations)). Нарушение `ImageParse` ключа не называет — только путь к файлу.

## Что сохраняется при экспорте и обратном импорте {#round-trip}

| Данные | Сохраняются при экспорте и импорте? |
|---|---|
| Узлы, поля, метки, счётчики, рёбра с их свойствами, схема, именованные запросы | Да. |
| Тела | Да, байт в байт. |
| Надгробия с причиной, заменой и помеченными блокерами | Да. |
| Конфликтные значения | Да. |
| [Файловые ссылки](file-links.html): файловые узлы, якоря, перемещения каталогов | Да. Цитаты якорей можно записывать целиком или только как дайджесты (`hash-only`). Где каждый файл находится прямо сейчас в конкретном рабочем дереве, не экспортируется; импортирующее хранилище находит файлы в своих деревьях. |
| Граф коммитов и метаданные коммитов (родители, слияния, синхронизации, исходные коммиты revert, актор, роль, сессия, сообщение) | Да, при гранулярности `commit`. |
| Id коммитов Moirai | Да, пересчитываются и проверяются. |
| Имена веток и тегов | Да. |
| Коммиты между двумя чекпоинтами | Нет, при гранулярности `checkpoint`: состояние в каждом чекпоинте точное, а путь к нему свёрнут. |
| Короткие id, например `#31` | По возможности, через побочный ref и карту алиасов. |
| Reflog, журнал операций и клиентские HEAD | Только с `--with-oplog`. |
| Структурные нарушения и выбор, сделанный при разрешении | Нет, так задумано: нарушения живут только на промежуточных refs, а разрешение экспортируется как значение, которое оно дало. |
| Аренды, маркеры завершения и удаления, результаты идемпотентности, счётчик id, внутренние снимки | Нет, так задумано: это состояние времени выполнения. Импортирующее хранилище заново выводит свои маркеры из импортированных коммитов и слияний. |
| Производное состояние, например очередь готовых задач | Вычисляется заново, никогда не записывается. |
| Собственные байты файлов хранилища | Нет: образ — логическая копия, а не резервная копия файлов. Для этого у Moirai есть отдельная команда `moirai backup`. |

Проект формулирует эти свойства как тесты. При гранулярности `commit` экспорт, импорт в новое хранилище и повторный экспорт должны давать побайтно одинаковые объекты и refs — в масштабе 100&nbsp;000 узлов и 100&nbsp;000 коммитов, в обоих форматах объектов. При гранулярности `checkpoint` каждая экспортированная ветка должна приходить с идентичным состоянием, а задачи за помеченными блокерами должны по-прежнему оставаться вне очереди готовых задач.

## Git не обязателен {#git-optional}

Moirai никогда не требует git. Без программы `git`, без git-библиотеки и без репозитория в нём всё равно работает всё: команды чтения и записи, ветки и слияния, теги, undo и revert, хуки, MCP-сервер, все запросы, а также `image export` и `image import` в локальный каталог репозитория или bundle-файл и обратно.

Это возможно потому, что у Moirai есть собственный слой git-объектов, написанный с нуля и работающий внутри процесса. Он читает и пишет отдельные (loose) объекты, pack-файлы и их индексы, файлы commit-graph, отдельные refs и `packed-refs` по протоколу lock-файлов git, а также bundles — в SHA-1 и SHA-256 — и читает репозитории, которые хранят refs в формате reftable. Никакая git-библиотека не линкуется, и проверка зависимостей при сборке это запрещает. Консольная утилита git служит независимой проверкой в тестах, а если она установлена, то и в четырёх необязательных местах, перечисленных ниже.

Читая файлы git прямо внутри процесса, без запуска git, Moirai находит репозиторий, в котором выполняется команда, записывает, в каком git-коммите, ветке и рабочем дереве сделана запись, и отвечает на вопрос «является ли этот git-коммит предком вершины рабочего дерева?» для своих команд `check` и `stale`. Сам `git` он запускает, только если git установлен, и только в четырёх явных необязательных местах: `image push` и `image pull` (иначе печатает команду); обновление refs в репозитории образа, который использует reftable; `moirai doctor lanes --refresh-graph`; и `moirai file mv --git`. Ни одно из них не лежит на пути чтения, запроса, захвата задачи или хука.

### Где лежит хранилище {#store-location}

Само хранилище в образ не входит: это каталог двоичных файлов, которые пишет только Moirai. Куда его помещает `moirai init` и как команда его находит, описано на странице о движке, в разделе [Где лежит хранилище](engine.html#store-location). Внутри git-репозитория хранилище помещается в собственный каталог git, в `<git-common-dir>/moirai/`, и удаляется вместе с этим каталогом. Это ещё одна причина для ежедневного экспорта и для `moirai backup`.
